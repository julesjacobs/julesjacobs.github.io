OxCaml Basics

Checked control over parallelism, allocation, and representation

A three-hour technical course for OCaml engineers learning OxCaml's performance-oriented type system.

Keep this minimal. The slides are the live teaching path; the course pages are the reference material.

The route

  1. 00Why OxCaml existschecked low-level intent
  2. 01Parallelismcontention and portability
  3. 02Allocationlocality, stack_, exclave_

Each topic is a checked lever: race safety, lifetime/allocation, and runtime layout.

Why OxCaml exists

OCaml default

Safe, high-level, uniform values, GC-managed allocation.

OxCaml addition

Explicit compiler-checked control when the default costs too much.

The goal

Checked low-level intent, not unsafe faster OCaml.

Frame every feature as making a performance-relevant fact visible to the type checker.

Three failure classes

Data race

Overlapping mutable access when at least one access writes.

Dangling stack pointer

A local value escapes the region that owns it.

Representation mismatch

Code expects one value word, but the caller has raw or product layout.

In all three cases, OxCaml turns a runtime failure mode into a compile-time error.

This primes the lecture around error reading, not feature memorization.

Level 0 Parallel work can overlap

fork_join2

let #(left, right) =
  Parallel.fork_join2 parallel
    (fun _parallel -> left_work ())
    (fun _parallel -> right_work ())
in
combine left right

Children may overlap; parent resumes after both finish.

spawn

let _ = Concurrent.spawn
  (fun () -> worker ())
  () in
parent_side_effect ()

Spawned work may overlap later parent effects.

The operational shape motivates the different callback requirements later.

Level 0 Parallel mutation can race

danger shape

let r = ref 0

Parallel.fork_join2 parallel
  (fun _ -> incr r)
  (fun _ -> incr r)

Both callbacks may touch the same mutable cell at the same time.

overlap rule

readwrite
readsaferace
writeracerace

Two reads are fine. Anything overlapping a write needs ownership or synchronization.

No modes yet. Students only need the programming problem.

Level 1 Direct body check is a first model

captured mutable state

let x = { hits = 0 }

Parallel.fork_join2 parallel
  (fun _ -> x.hits <- x.hits + 1)
  (fun _ -> x.hits <- x.hits + 1)

The callback body directly writes state captured from outside.

fresh mutable state

let _ = Concurrent.spawn
  (fun () ->
     let x = { hits = 0 } in
     x.hits <- x.hits + 1)
  () in
()

Fresh state created inside the callback is owned by that callback body.

Useful simplification: the compiler appears to check callback bodies. It is not just scanning syntax.

This model predicts simple direct-access examples, then motivates modes.

Level 1 Fresh per-call buffer

Each call owns its buffer. Parallel calls mutate separate scratch state.

Browser playground note: the API names are real, but JavaScript runs the scheduler and spawn shim sequentially.

spawn_fresh_buffer.ml
let bits_to_string bits = let buf = Buffer.create 0 in List.iter (fun bit -> Buffer.add_char buf (if bit then '1' else '0')) bits; Buffer.contents buf let () = print_endline "The output is:"; let _ = Concurrent.spawn (fun () -> print_endline (bits_to_string [true; false; true])) () in print_endline (bits_to_string [false; true; false])
Ask where the mutable object is allocated. The answer is inside each call.

Level 2 Contention modes describe mutable access

x @ uncontended
  • read and write mutable fields
  • ordinary single-owner access
→
x @ shared
  • read mutable fields
  • no mutable writes
→
x @ contended
  • immutable fields only
  • some other user may write

Contention answers: at this use site, what access do I have to mutable components?

Use the single-writer or many-readers invariant. Do not conflate shared with shareable.

Level 2 Field access has mode requirements

immutable field

x.id

works even when x is contended

mutable read

x.hits

needs x at least shared

mutable write

x.hits <- x.hits + 1

needs x @ uncontended

A direct field operation succeeds or fails according to the available contention mode.

This is the precise replacement for the direct body scan model.

Level 3 Closure boundaries weaken captures

fork/join callback boundary

structured parallel callback

b @ uncontended→b @ shared
a @ shared→a @ shared
c @ contended→c @ contended

Mutable reads can survive; mutable writes cannot.

spawn callback boundary

detached parallel callback

b @ uncontended→b @ contended
a @ shared→a @ contended
c @ contended→c @ contended

Captured mutable reads and writes are both unavailable.

The callback boundary controls how captured values are seen inside the body.

Outside the closure, the original binding still has its original mode.

Level 3 Captured x in three contexts

ordinary

x @ uncontended

  • x.id ok
  • x.hits ok
  • x.hits <- ... ok

fork/join

x @ shared

  • x.id ok
  • x.hits ok
  • x.hits <- ... rejected

spawn

x @ contended

  • x.id ok
  • x.hits rejected
  • x.hits <- ... rejected
This resolves why fork/join and spawn differ before API types are introduced.

Level 4 Explicit argument requirements

A helper’s type records what mode each explicit argument requires.

The compiler does not need to inline the helper body.

In inferred interfaces, plain t means the default requirement: t @ uncontended.

Inside fork/join, x may be only shared; bump_hits requires uncontended.

mode_access.ml
type t = { id : int; mutable hits : int } let get_id (x @ contended) = x.id let get_hits (x @ shared) = x.hits let bump_hits (x @ uncontended) = x.hits <- x.hits + 1
Highlight immutable read, mutable read, mutable write.

Level 5 Portability axis

portable
  • detached parallel work
  • closures keep no mutable access
→
shareable
  • structured fork/join work
  • closures keep read-only access
→
nonportable

  • closures may keep read/write access

Portability answers: can this value be used in this parallel context? These are the names for the callback-boundary behaviors from Level 3.

For closures, portability mostly summarizes what the closure captured and how it may use those captures.

Level 5 Hidden captures travel with function values

write_x 1 has no explicit x argument.

The mutable access is hidden in the function value write_x.

So the call checks whether write_x is portable enough.

hidden_helpers.ml
type t = { id : int; mutable hits : int } let x = { id = 1; hits = 0 } let id_x () = x.id let read_x () = x.hits let write_x v = x.hits <- v let _ = let _ = Concurrent.spawn (fun () -> write_x 1) () in write_x 2
There is no explicit x argument in write_x 1. The danger is inside the closure value write_x.

Level 5 Shared buffer revisited

Moving buf to the top level makes bits_to_string_shared carry hidden mutable state.

Failure chain: captured buf → nonportable function value → spawn requires portable callback.

shared_buffer.ml
let buf = Buffer.create 0 let bits_to_string_shared bits = Buffer.clear buf; List.iter (fun bit -> Buffer.add_char buf (if bit then '1' else '0')) bits; Buffer.contents buf let () = print_endline "The output is:"; let _ = Concurrent.spawn (fun () -> print_endline (bits_to_string_shared [true; false; true])) () in print_endline (bits_to_string_shared [false; true; false])

Level 5 Two questions per call

explicit argument failure

let bump_hits (x @ uncontended) =
  x.hits <- x.hits + 1

fun _parallel -> bump_hits x

Is x available at the parameter mode?

function-value failure

let write_x v =
  x.hits <- v

fun _parallel -> write_x 1

Is write_x itself shareable or portable enough?

For any call inside parallel work, ask both questions: arguments and callee value.

Level 6 Modes are positional

t @ shared

this value position requires shared contention

(unit -> unit) @ portable

this function value must be portable

('a @ shared -> 'b) @ shareable

callback value is shareable; its argument is provided as shared

((unit -> unit) @ portable -> unit) @ shareable

outer function is shareable; its argument must be a portable function

Do not split “values vs functions.” Function values are values; read the annotation at its type position.

This prepares students for real signatures.

Level 7 Parallel APIs are ordinary typed APIs

val fork_join2 :
  Parallel.t @ local ->
  (Parallel.t @ local -> 'a) @ shareable ->
  (Parallel.t @ local -> 'b) @ shareable ->
  #('a * 'b)

val spawn :  (* schematic *)
  (unit -> unit) @ portable ->
  unit -> unit

The callback argument types trigger the earlier rules. The real spawn API also tracks once/unique/unyielding details and returns a spawn_result.

No compiler magic for these names. The callback slots impose the modal requirements.

Level 8 Exercise: parallel_map shape

The callback mode propagates through higher-order helper APIs.

Predict the inferred promise on f: both fork/join callbacks must be allowed to call it.

parallel_map.ml
let rec parallel_map parallel f xs = match xs with | [] -> [] | x :: xs -> let #(y, ys) = Parallel.fork_join2 parallel (fun _parallel -> f x) (fun parallel -> parallel_map parallel f xs) in y :: ys
This is intentionally a mode-reading exercise, not a long coding exercise.

Level 8 Read the capstone type positionally

val parallel_map :
  Parallel.t @ local ->
  ('a @ shared -> 'b) @ shareable ->
  'a list @ shareable shared ->
  'b list @@ stateless

callback: shareable value; receives each element as shared

input list: may flow into fork/join work; read-only access

implementation: inferred stateless, which implies portable

Use this as API-design discussion: what should be shareable, portable, shared, or local?

Parallelism recap

0. Parallel mutation can race.

1. Surface model: callback bodies appear to be checked.

2. Direct reads/writes require contention modes.

3. Shareable and portable closure boundaries weaken captured values.

4. Function calls check explicit argument-mode requirements.

5. Function values carry portability, catching hidden captures.

6-8. Modes are positional; ordinary API types create reusable parallel contracts.

Module 02

Locality and stack allocation

  • Explain why heap allocation matters in hot paths.
  • Use local arguments and local returns.
  • Predict stack escape errors.
  • Use modalities to preserve global fields inside local containers.
Shift from race safety to lifetime and heap allocation.

Why heap allocation matters

OCaml allocation is usually cheap. Some hot or low-latency paths still need explicit control over whether temporary values go on the GC heap or the allocation stack.

Some n is ordinary style, but the present case allocates.

Ex03_motivating_option_allocation.ml
let maybe_positive n = if n >= 0 then Some n else None let () = match maybe_positive 3 with | None -> print_endline "none" | Some n -> print_endline (string_of_int n)
The point is not that option is bad. The point is that some APIs need allocation behavior in the contract.

Three storage places

Use the tabs to compare ordinary heap allocation, stack allocation, rejected escape, and exclave_.

stack_ succeeds when consumed locally

stack_ forces the following allocation onto the allocation stack.

The consumer matters: sum accepts int list @ local.

Ex03_stack_list_used_inside_region.ml
let rec sum_loop acc (xs : int list @ local) = match xs with | [] -> acc | x :: xs -> sum_loop (acc + x) xs let sum (xs : int list @ local) = sum_loop 0 xs let () = print_endline (string_of_int (sum (stack_ [1; 2; 3])))
Explain that local is a promise by the callee: it will not retain the list.

stack_ rejects escapes

stack_ is strict: it does not silently move an escaping allocation back to the heap.

Expected outcome: rejected escape.

Ex03_stack_list_escape_global_return.ml
let bad () = stack_ [1; 2; 3]
Tie this to the dangling pointer diagram: the callee region would be reclaimed.

Local arguments let APIs borrow values

The restriction is on the function body, not on callers.

Callers may pass heap values or stack values.

Ex03_local_consumer.ml
let inspect (x : int option @ local) = match x with | None -> 0 | Some n -> n let demo () = inspect (stack_ (Some 42)) [@nontail]
Ask: who is restricted? Answer: inspect's implementation.

Ordinary callback slots cannot borrow stack state

A parameter of type scratch -> 'a asks for a global scratch argument.

That is necessary because the callback type would allow the function to retain its argument.

Expected outcome: rejected at f s; this API did not promise borrowing.

Ex03_with_scratch_escape.ml
type scratch = { mutable total : int } let saved : scratch option ref = ref None let with_scratch_bad (f : scratch -> 'a) = let s = stack_ { total = 0 } in f s [@nontail] let bad () = with_scratch_bad (fun s -> saved := Some s)
The saved ref shows why the ordinary callback type is unsafe for stack state, even though the type checker rejects at the call.

Local callback parameters express borrowing

A callback can use temporary state during the call, but cannot retain it.

The local parameter is the API contract.

Ex03_with_scratch_local_callback.ml
type scratch = { mutable total : int } let with_scratch (f : scratch @ local -> 'a) = let s = stack_ { total = 0 } in f s [@nontail] let add_with_scratch x y = with_scratch (fun s -> s.total <- x + y; s.total)
This is borrowing, not just allocation optimization.

Local closures need local callback slots

If a closure captures a local value, the closure itself is local.

An ordinary unit -> unit slot is too global for that closure.

let call_now_bad (f : unit -> unit) =
  f ()

Immediate-call APIs should accept local callback values.

Ex03_local_callback_slot.ml
let bump (r : int ref @ local) = r := !r + 1 let call_now (f : (unit -> unit) @ local) = f () let good () = let count = stack_ (ref 0) in call_now (fun () -> bump count); !count
Contrast with an ordinary callback slot, which would allow the closure to escape.

Local returns and exclave_

exclave_ exits the current region and evaluates the result expression in the parent region.

The result may be local to the caller.

Ex03_exclave_return.ml
let make_stack_list () : _ @ local = exclave_ stack_ [1; 2; 3] let rec sum acc (xs : int list @ local) = match xs with | [] -> acc | x :: xs -> sum (acc + x) xs let () = print_endline (string_of_int (sum 0 (make_stack_list ())))
Do not describe exclave_ as smuggling out an existing local value. It builds the result in the parent region.

Runtime placement and mode view are different facts

stack data

Must be viewed as @ local.

heap data

Can be viewed as @ local by submoding.

@@ global

Preserves the global view across a field boundary.

Make the distinction explicit: runtime heap placement is not the same thing as the current compile-time mode view.

Submoding: use global data locally

escape xs stores the list in a global ref, so xs is usable globally.

sum xs then uses the same value through the more restrictive @ local view.

Ex03_submoding_global_inner_used_locally.ml
let saved : int list option ref = ref None let escape xs = saved := Some xs let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x :: xs -> x + sum xs let demo () = let xs = [1; 2; 3] in escape xs; sum xs let () = print_endline (string_of_int (demo ()))
Submoding is safe weakening: a global value can be used by an API that only promises local use.

Plain local containers lose the global view

The inner list starts global: the first escape inner type-checks.

After matching through outer : int list list @ local, the extracted inner is only local.

Ex03_plain_local_outer_list_forgets_global_inner.ml
let saved : int list option ref = ref None let escape xs = saved := Some xs let demo () = let inner = [1; 2; 3] in escape inner; let outer = stack_ [inner] in match outer with | [] -> () | inner :: _ -> escape inner
The point is precision loss through an ordinary constructor field, not that the original heap list became unsafe at runtime.

Modalities preserve the global view

Modes.Global.t has a field with modality @@ global.

The outer list can be local while inner.global is still known to be global.

Ex03_global_wrapper_preserves_inner_list_globality.ml
let saved : int list option ref = ref None let escape xs = saved := Some xs let demo () = let inner = [1; 2; 3] in escape inner; let outer = stack_ [{ Modes.Global.global = inner }] in match outer with | [] -> () | inner :: _ -> escape inner.global
Phrase this as a field-boundary rule, not a cast. The wrapper can only be built from a global value.

Some values cross locality

Immediate

let id_local_int (x : int @ local) : int =
  x

No lifetime-sensitive heap block.

Pointer

let id_local_string
  (x : string @ local) : string @ global =
  x

Rejected: the string may point into a local region.

This prepares the representation section: locality depends on whether there may be a pointer whose lifetime matters.

Allocation recap

local/global controls lifetime and escape.

stack_ forces the next allocation onto the allocation stack.

exclave_ builds a local result in the caller region.

Keep the focus on lifetime control and where temporary blocks live.

Module 03

Value layouts and unboxing

  • Explain immediate words vs heap-block pointers.
  • Spot boxes, headers, pointers, and raw fields.
  • Choose the feature that removes a specific cost.
  • Read layout and kind requirements in APIs.
Start from the ordinary OCaml runtime invariant, then show where it costs.

Runtime invariant: every OCaml value is one word

Immediate value

63 bits of immediate data1

int, char, bool, unit, etc. use this shape.

Pointer value

aligned heap address0
heap block
header wordsize, tag, scan info
payload 0value or raw data
...
payload Nvalue or raw data

Records, tuples, arrays, etc. use this shape.

Avoid over-detailing endianness. The key fact is low-bit interpretation.

Heap block anatomy

heap block
header wordsize, tag, scan info
payload 0value or raw data
payload 1value or raw data
payload Nvalue or raw data

The header describes which fields are values vs. raw data. The GC does not scan raw data.

This distinction matters for unboxed float fields and mixed blocks.

Uniform value representation is powerful

Source

let plain_value_integer = 5

let plain_value_tuple = (1, 2, 3)

type quote =
  { symbol : string
  ; price : int
  ; mutable size : int
  }

Runtime model

The runtime, GC, and libraries all agree on one value shape. Polymorphic functions are only compiled once.

The uniform model is a strength before it is a cost.

Variants are values too

Constant constructors

Represented as immediates.

Payload constructors

Allocate heap blocks; the header tag identifies the constructor.

Recursive data is a graph of values: immediates or pointers to other heap blocks.

This is where the representation visualizer is strongest in the course page.

Sharing: the heap is a graph

let shared = "shared"
let t = (shared, shared, "other")

Two fields can point at the same heap object.

Do not redraw shared heap graphs as trees.

Uniform model costs: boxes and pointers

boxed numeric values

let boxed_numeric_values =
  (3.5, 456L)

tuple block, boxed float, boxed int64

ordinary option values

let ordinary_option_values =
  (None, Some "found")

Some constructor requires a block

Boxes mean allocation, headers, pointer indirection, and future GC work.

Unboxed types remove specific boxes

ordinary tuple

(1, "one")

one heap block for grouping

unboxed tuple

#(1, "one")

tuple block removed; string heap object remains

Unboxing removes the specified box, not everything reachable.

Unboxed records inline nested fields

mixed boxed point

type boxed_point =
  { x : float; y : float; label : string }

type sample =
  { point : boxed_point
  ; count : int
  }

mixed ordinary record: float fields are boxed value fields

mixed unboxed point

type unboxed_point =
  #{ x : float#; y : float#; label : string }

type sample =
  { point : unboxed_point
  ; count : int
  }

raw float fields and the label pointer are stored inline

This is the most concrete representation win in the lecture.

or_null removes option wrapper allocation

None → Null missing value
Some payload → This payload same representation as the payload
exercise_hd_or_null.ml
let hd_option = function | [] -> None | x :: _ -> Some x let hd_or_null xs = failwith "implement this"
Ask students to rewrite option first, then discuss representation.

or_null answer

Null replaces None.


This x replaces Some x without adding a wrapper block around x.

exercise_hd_or_null.ml
let hd_option = function | [] -> None | x :: _ -> Some x let hd_or_null = function | [] -> Null | x :: _ -> This x
The important representation fact is that This x has x's representation, while Some x normally allocates an option block.

The limit: or_null cannot be nested

Null is represented by the null machine word.


If string or_null or_null were allowed, the same null word would need two meanings: the outer missing value and the inner missing value.


The payload of or_null must be non-null. A value that is already or_null is maybe-null.

or_null_cannot_be_nested.ml
type nested = string or_null or_null
Put this after the allocation win: first teach the useful representation, then show the boundary condition.

Kinds record allowed representations

If an error says a type parameter expects value, the API expects ordinary one-word OCaml values.


Edit the kind bound from value to float64.

exercise_value_kind_rejects_float.ml
type ('a : value) box type bad = float# box
The fix is float64. For an unboxed product, use product layouts such as value & float64.

Abstract types need public kinds

bad for an unboxed point

module type Point = sig
  type t
  val make : float# -> float# -> t
end

plain abstract type defaults to value, losing the product layout

fixed signature

module type Point = sig
  type t : float64 & float64
  val make : float# -> float# -> t
end

representation remains abstract; kind is public

Kinds are part of the calling convention even when fields remain hidden.

Polymorphic code still has a layout

ordinary map

val map_value
  :  ('a : value) ('b : value)
  .  ('a -> 'b)
  -> 'a list
  -> 'b list

product layout map

type ('a : value & value) product_list = ...

val map_product_list
  :  ('a : value & value) ('b : value & value)
  .  ('a -> 'b)
  -> 'a product_list
  -> 'b product_list
Code must know how many components are passed, returned, stored, and scanned.

Templates reduce layout-specific repetition

let%template[@kind k = (value, value & value)] id
  : ('a : k). 'a -> 'a =
  fun x -> x

One source pattern can generate multiple definitions with different calling conventions.

Keep this as recognition material, not a deep ppx_template lesson.

Choose the correct lever

Data race safety

Use contention and portability requirements.

Lifetime correctness or heap allocation cost

Use local, stack_, and exclave_.

Box or pointer cost

Use layouts, unboxed types, and or_null.

All three make performance-sensitive intent explicit and checked.
