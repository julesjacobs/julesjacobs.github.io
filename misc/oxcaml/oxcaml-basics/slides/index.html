Why does OxCaml exist?

Upstream OCaml

Safe, high-level, uniform values, with GC-managed allocation.

OxCaml

Explicit control when the default costs too much, without sacrificing safety.

The goal

Safe, predictable control over performance-critical aspects of program behavior.

Frame every feature as making a performance-relevant fact visible to the type checker.

Three classes of failure

Data race

Overlapping mutable access when at least one access writes.

Dangling stack pointer

A local value escapes the region that owns it.

Representation mismatch

Data has the wrong in-memory layout.

In all three cases, OxCaml turns a runtime failure mode into a compile-time error.

This primes the lecture around error reading, not feature memorization.

Using parallelism to speed up your code

fork_join2

let #(left, right) =
  Parallel.fork_join2 parallel
    (fun _parallel -> left_work ())
    (fun _parallel -> right_work ())
in
combine left right

Children run in parallel; parent resumes after both finish.

spawn

let _ =
  Concurrent.spawn spawn
    ~f:(fun _scope _ctx _conc -> worker ())
in
parent_side_effect ()

Spawned worker runs in parallel; parent continues immediately.

The operational shape motivates the different function requirements later.

Example: Doing work in parallel

fork_join_fresh_buffer.ml
let bits_to_string bits = let buf = Buffer.create 0 in List.iter (fun bit -> Buffer.add_char buf (if bit then '1' else '0')) bits; Buffer.contents buf let strings_in_parallel parallel = let #(left, right) = Parallel.fork_join2 parallel (fun _parallel -> bits_to_string [true; false; true]) (fun _parallel -> bits_to_string [false; true; false]) in left ^ "\n" ^ right let () = let scheduler = Parallel.Scheduler.Sequential.create () in let s = Parallel.Scheduler.Sequential.parallel scheduler ~f:strings_in_parallel in print_endline "The output is:"; print_endline s
Ask where the mutable object is allocated. The answer is inside each call.

Unsafe optimization: pull the buffer allocation to the top level

fork_join_shared_buffer.ml
let buf = Buffer.create 0 let bits_to_string bits = Buffer.clear buf; List.iter (fun bit -> Buffer.add_char buf (if bit then '1' else '0')) bits; Buffer.contents buf let strings_in_parallel parallel = let #(left, right) = Parallel.fork_join2 parallel (fun _parallel -> bits_to_string [true; false; true]) (fun _parallel -> bits_to_string [false; true; false]) in left ^ "\n" ^ right
This is the same program shape, but moving the allocation changes one-buffer-per-call into one shared buffer.

What went wrong: data race!

Bad: two parallel writes to the same buffer.

What is a data race?

danger shape 1: two writes

let r = ref 0

Parallel.fork_join2 parallel
  (fun _ -> incr r)
  (fun _ -> incr r)

danger shape 2: one write and one read

let r = ref 0

Parallel.fork_join2 parallel
  (fun _ -> incr r)
  (fun _ -> !r)

overlap rule

readwrite
readsaferace
writeracerace

Two parallel reads are fine. Two racing writes are not allowed. A racing read and write is not allowed either.

No modes yet. Students only need the programming problem.

The OxCaml compiler checks for data races

danger shape 1: two writes
let bad_two_writes parallel = let r = ref 0 in Parallel.fork_join2 parallel (fun _parallel -> incr r) (fun _parallel -> incr r)
danger shape 2: one write and one read
let bad_read_and_write parallel = let r = ref 0 in Parallel.fork_join2 parallel (fun _parallel -> incr r) (fun _parallel -> !r)
The examples take parallel as an argument so the slide can focus on the checked worker functions, not scheduler setup.

Field access has mode requirements

This is the contrast case before the key point: not every closure boundary weakens modes; the closure's required mode determines the effect.

Key point: a variable's type never changes, but a variable's mode can change when it crosses a closure boundary.

Function arguments have modes

Function argument modes record what level of access the function needs.

function_argument_modes.ml
type t = { id : int; mutable hits : int } let get_hits (x @ shared) = x.hits let bump_hits (x @ uncontended) = x.hits <- x.hits + 1 let demo parallel x = Parallel.fork_join2 parallel (fun _parallel -> get_hits x) (fun _parallel -> bump_hits x)
The first function can call get_hits because captured x is shared inside fork/join. The second function cannot call bump_hits because bump_hits requires uncontended access.

The type of fork_join2 and spawn

val fork_join2 :
  Parallel.t @ local ->
  (Parallel.t @ local -> 'a) @ shareable ->
  (Parallel.t @ local -> 'b) @ shareable ->
  #('a * 'b)

val spawn :  (* schematic *)
  ('scope_ctx, 'ctx) spawn ->
  f:('scope_ctx Concurrent.Scope.t -> 'ctx -> 'ctx Concurrent.t -> unit) @ portable ->
  unit
No compiler magic for these names. The function argument slots impose the modal requirements.

Parallelism recap

0. Parallel mutation can race.

1. Simple model: functions passed to parallel work are checked.

  • Fork/join can read but not write mutable fields.
  • Spawn can neither read nor write mutable fields.

2. Reads and writes are checked using the contention axis.

3. Functions are checked using the portability axis.

Why heap allocation matters

OxCaml allocation is cheap, but GC is high latency.

Solution

stack allocation

Set up the allocation section before showing the small option example.

A small stack allocation example

Stack allocate values with stack_.

The allocation stack gets cleared at the end of a function.

Ex03_stack_sum.ml
let rec sum xs = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in (* xs gets deallocated here *) n let () = let n = sum3 1 2 3 in print_endline (string_of_int n)
The temporary list is allocated inside sum3, consumed there, and cleared when sum3 returns.

Stack allocated values can escape their region 😨

A callee cannot secretly keep a stack-allocated value after the caller region is gone.

Expected outcome: the call to sum is rejected.

Ex03_stack_sum_escape.ml
let saved = ref [] let rec sum xs = match xs with | [] -> 0 | x::xs' -> saved := xs; x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in n let () = let n = sum3 1 2 3 in print_endline (string_of_int n)
The ref is global, so assigning xs would keep a pointer into a stack region after the function returns.

Returning stack allocated values escapes their region 😨

The integer result can return, but the stack-allocated list cannot.

Expected outcome: returning xs is rejected.

Ex03_stack_sum_return_escape.ml
let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in n, xs let () = let n, _xs = sum3 1 2 3 in print_endline (string_of_int n)
Returning the pair would keep xs alive after sum3's allocation stack region is cleared.

But sometimes we want to return stack allocated values:
exclave_

exclave_ builds the returned value in the caller's region.

The caller can use the returned list as a local value.

Ex03_stack_sum_exclave_return.ml
let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = exclave_ let xs = stack_ [a;b;c] in let n = sum xs in n, xs let () = let n, xs = sum3 1 2 3 in print_endline (string_of_int n); print_endline (string_of_int (sum xs))
The returned list is not smuggled out of sum3's region; it is allocated in the caller's region after exclave_.

How OxCaml manages the allocation stack

Normal function

let f x =
  ...
  result
compiles to
let f x =
  start_new_region ();
  ...
  end_current_region ();
  result

exclave_ result

let f x =
  exclave_
  ...
  result
compiles to
let f x =
  ...
  result
The point is operational: ordinary calls get a fresh allocation-stack region; exclave_ moves result construction to the parent region instead.

How OxCaml manages the allocation stack: tail calls

Tail-call function

let rec loop x =
  ...
  loop next_x
compiles to
let rec loop x =
  start_new_region ();
  ...
  end_current_region ();
  tail call loop next_x

Non-tail call

let f x =
  ...
  g x [@nontail]
compiles to
let f x =
  start_new_region ();
  ...
  let result = g x in
  end_current_region ();
  result

[@nontail] suppresses the tail call, so the region ends only after the call returns.

A tail call is not a normal return of a variable. The current region must be cleared before control transfers to the next call. Use [@nontail] when a local value must stay alive during the call.

How OxCaml manages the allocation stack: mid-function exclave_

Middle exclave_

let f x =
  let y = prepare x in
  exclave_
  build_result y
compiles to
let f x =
  start_new_region ();
  let y = prepare x in
  end_current_region ();
  build_result y

If exclave_ is at the beginning, OxCaml starts the region and ends it immediately.

That has the same effect as not starting a region.

The subtle case is not an entirely exclaved function. Work before exclave_ still belongs to the function's own region; the region ends at the exclave_ point.

Regional is the middle lifetime fact: the value can survive the current region ending, but may still belong to some higher-up region.

Idiom: borrowing

The with_scratch body can use the temporary state during the call, but cannot retain it, forced by the @ local parameter.

Ex03_with_scratch_local_function.ml
type scratch = { mutable total : int } let with_scratch (f : scratch @ local -> 'a) = let s = stack_ { total = 0 } in f s [@nontail] let add_with_scratch x y = with_scratch (fun s -> s.total <- x + y; s.total)
This is borrowing, not just allocation optimization.

Local closures need local function slots

If a closure captures a local value, the closure itself is local.

An ordinary unit -> unit slot is too global for that closure.

let call_now_bad (f : unit -> unit) =
  f ()

Immediate-call functions should accept local function values.

Ex03_local_function_slot.ml
let bump (r : int ref @ local) = r := !r + 1 let call_now (f : (unit -> unit) @ local) = f () let good () = let count = stack_ (ref 0) in call_now (fun () -> bump count); !count
Contrast with an ordinary function slot, which would allow the closure to escape.

Local returns and exclave_

exclave_ exits the current region and evaluates the result expression in the parent region.

The result may be local to the caller.

Ex03_exclave_return.ml
let make_stack_list () : _ @ local = exclave_ stack_ [1; 2; 3] let rec sum acc (xs : int list @ local) = match xs with | [] -> acc | x :: xs -> sum (acc + x) xs let () = print_endline (string_of_int (sum 0 (make_stack_list ())))
Do not describe exclave_ as smuggling out an existing local value. It builds the result in the parent region.

Submoding: use global data locally

escape xs stores the list in a global ref, so xs is usable globally.

sum xs then uses the same value through the more restrictive @ local view.

Ex03_submoding_global_inner_used_locally.ml
let saved : int list option ref = ref None let escape xs = saved := Some xs let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x :: xs -> x + sum xs let demo () = let xs = [1; 2; 3] in escape xs; sum xs let () = print_endline (string_of_int (demo ()))
Submoding is safe weakening: a global value can be used by an API that only promises local use.

Plain local containers lose the global view

The inner list starts global: the first escape inner type-checks.

After matching through outer : int list list @ local, the extracted inner is only local.


Reason: modes are deep.


Modes apply all the way down in a data structure.

Ex03_plain_local_outer_list_forgets_global_inner.ml

Modalities preserve the global view

The outer list is local, while the inner list is global.

A local list of global lists: the field modality preserves the global view.

Ex03_global_wrapper_preserves_inner_list_globality.ml
type 'a global = { global : 'a @@ global } let saved : int list option ref = ref None let escape xs = saved := Some xs let demo () = let inner = [1; 2; 3] in escape inner; let outer = stack_ [{ global = inner }] in match outer with | [] -> () | inner :: _ -> escape inner.global
Phrase this as a field-boundary rule, not a cast. The wrapper can only be built from a global value.

or_null answer

Null replaces None.


This x replaces Some x without adding a wrapper block around x.

exercise_hd_or_null.ml
let hd_option = function | [] -> None | x :: _ -> Some x let hd_or_null = function | [] -> Null | x :: _ -> This x
The important representation fact is that This x has x's representation, while Some x normally allocates an option block.

The limit: or_null cannot be nested

Null is represented by the null machine word.


If string or_null or_null were allowed, the same null word would need two meanings: the outer missing value and the inner missing value.


The payload of or_null must be non-null. A value that is already or_null is maybe-null.

or_null_cannot_be_nested.ml
type nested = string or_null or_null
Put this after the allocation win: first teach the useful representation, then show the boundary condition.

Kinds record allowed representations

If an error says a type parameter expects value, the API expects ordinary one-word OxCaml values.


Edit the kind bound from value to float64.

exercise_value_kind_rejects_float.ml
type ('a : value) box type bad = float# box
The fix is float64. For an unboxed product, use product layouts such as value & float64.

Abstract types need public kinds

bad for an unboxed point

module type Point = sig
  type t
  val make : float# -> float# -> t
end

plain abstract type defaults to value, losing the product layout

fixed signature

module type Point = sig
  type t : float64 & float64
  val make : float# -> float# -> t
end

representation remains abstract; kind is public

Kinds are part of the calling convention even when fields remain hidden.

Polymorphic code still has a layout

ordinary map

val map_value
  :  ('a : value) ('b : value)
  .  ('a -> 'b)
  -> 'a list
  -> 'b list

product layout map

type ('a : value & value) product_list = ...

val map_product_list
  :  ('a : value & value) ('b : value & value)
  .  ('a -> 'b)
  -> 'a product_list
  -> 'b product_list
Code must know how many components are passed, returned, stored, and scanned.

Templates reduce layout-specific repetition

let%template[@kind k = (value, value & value)] id
  : ('a : k). 'a -> 'a =
  fun x -> x

One source pattern can generate multiple definitions with different calling conventions.

Keep this as recognition material, not a deep ppx_template lesson.

Choose the correct lever

Data race safety

Use contention and portability requirements.

Lifetime correctness or heap allocation cost

Use local, stack_, and exclave_.

Box or pointer cost

Use layouts, unboxed types, and or_null.

All three make performance-sensitive intent explicit and checked.
