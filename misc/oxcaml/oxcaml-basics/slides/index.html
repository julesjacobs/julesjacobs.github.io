Why does OxCaml exist?

Upstream OCaml

Safe, high-level, uniform values, with GC-managed allocation.

OxCaml

Explicit control when the default costs too much, without sacrificing safety.

The goal

Safe, predictable control over performance-critical aspects of program behavior.

Frame every feature as making a performance-relevant fact visible to the type checker.

Three classes of optimization in OxCaml

Parallel work

Use more cores without introducing data races.

Stack allocation

Avoid heap allocation without creating dangling stack pointers.

Unboxed representation

Remove boxes and pointer hops without representation mismatches.

Each optimization has a matching safety check, so bugs become a compile-time error.

Start from what programmers want to optimize. Then explain that each optimization has a matching failure mode: data race, dangling stack pointer, or representation mismatch.

Using parallelism to speed up your code

fork_join2

let #(left, right) =
  Parallel.fork_join2 parallel
    (fun _parallel -> left_work ())
    (fun _parallel -> right_work ())
in
combine left right

Children run in parallel; parent resumes after both finish.

spawn

let _ =
  Concurrent.spawn spawn
    ~f:(fun _scope _ctx _conc -> worker ())
in
parent_side_effect ()

Spawned worker runs in parallel; parent continues immediately.

The operational shape motivates the different function requirements later.

Example: Doing work in parallel

fork_join_fresh_buffer.ml
let bits_to_string bits = let buf = Buffer.create 0 in List.iter (fun bit -> Buffer.add_char buf (if bit then '1' else '0')) bits; Buffer.contents buf let strings_in_parallel parallel = let #(left, right) = Parallel.fork_join2 parallel (fun _parallel -> bits_to_string [true; false; true]) (fun _parallel -> bits_to_string [false; true; false]) in left ^ "\n" ^ right let () = let scheduler = Parallel.Scheduler.Sequential.create () in let s = Parallel.Scheduler.Sequential.parallel scheduler ~f:strings_in_parallel in print_endline "The output is:"; print_endline s
Ask where the mutable object is allocated. The answer is inside each call.

Unsafe optimization: pull the buffer allocation to the top level

fork_join_shared_buffer.ml
let buf = Buffer.create 0 let bits_to_string bits = Buffer.clear buf; List.iter (fun bit -> Buffer.add_char buf (if bit then '1' else '0')) bits; Buffer.contents buf let strings_in_parallel parallel = let #(left, right) = Parallel.fork_join2 parallel (fun _parallel -> bits_to_string [true; false; true]) (fun _parallel -> bits_to_string [false; true; false]) in left ^ "\n" ^ right
This is the same program shape, but moving the allocation changes one-buffer-per-call into one shared buffer.

The shared buffer creates a data race

Two parallel writes target the same buffer.

What is a data race?

danger shape 1: two writes

let r = ref 0

Parallel.fork_join2 parallel
  (fun _ -> incr r)
  (fun _ -> incr r)

danger shape 2: one write and one read

let r = ref 0

Parallel.fork_join2 parallel
  (fun _ -> incr r)
  (fun _ -> !r)

overlap rule

readwrite
readsaferace
writeracerace

Two parallel reads are fine. Two racing writes are not allowed. A racing read and write is not allowed either.

No modes yet. Students only need the programming problem.

The OxCaml compiler checks for data races

danger shape 1: two writes
let bad_two_writes parallel = let r = ref 0 in Parallel.fork_join2 parallel (fun _parallel -> incr r) (fun _parallel -> incr r)
danger shape 2: one write and one read
let bad_read_and_write parallel = let r = ref 0 in Parallel.fork_join2 parallel (fun _parallel -> incr r) (fun _parallel -> !r)

Function arguments have modes

Function argument modes record what level of access the function needs.

Why stack allocation matters

OxCaml allocation is cheap, but GC is high latency.

Solution

stack allocation

Set up the allocation section before showing the small option example.

A small stack allocation example

Stack allocate values with stack_.

OxCaml can often infer stack allocation; stack_ makes it a requirement.

The current allocation region is cleared before the function returns.

Ex03_stack_sum.ml
(* Stack allocation example. *) let rec sum xs = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in (* xs gets deallocated here *) n let () = let n = sum3 1 2 3 in print_endline (string_of_int n)
The temporary list is allocated inside sum3, consumed there, and cleared when sum3 returns.

Stack allocated values cannot escape their region

A callee cannot secretly keep a stack-allocated value after the caller region is gone.

Expected outcome: the call to sum is rejected.

Ex03_stack_sum_escape.ml
(* Stack allocation example. *) let saved = ref [] let rec sum xs = match xs with | [] -> 0 | x::xs' -> saved := xs; x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in (* xs gets deallocated here *) n let () = let n = sum3 1 2 3 in print_endline (string_of_int n)
The ref is global, so assigning xs would keep a pointer into a stack region after the function returns.

Returning stack allocated values can escape their region

The integer result can return, but the stack-allocated list cannot.

Expected outcome: returning xs is rejected.

Ex03_stack_sum_return_escape.ml
(* Stack allocation example. *) let rec sum xs = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in (* xs gets deallocated here *) n, xs let () = let n, _xs = sum3 1 2 3 in print_endline (string_of_int n)
Returning the pair would keep xs alive after sum3's allocation stack region is cleared.

But sometimes we want to return stack allocated values

exclave_ builds the returned value in the caller's region.

The caller can use the returned list as a local value.

Ex03_stack_sum_exclave_return.ml
(* Stack allocation example. *) let rec sum xs = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = exclave_ let xs = stack_ [a;b;c] in let n = sum xs in n, xs let () = let n, xs = sum3 1 2 3 in print_endline (string_of_int n); print_endline (string_of_int (sum xs))
The returned list is not smuggled out of sum3's region; the result construction belongs to the caller's region.

How OxCaml manages the allocation stack

OxCaml stack allocations use a separate allocation stack, reclaimed at region boundaries.

Normal function

let f x =
  ...
  result
compiles to
let f x =
  start_new_region ();
  ...
  end_current_region ();
  result

exclave_ result

let f x =
  exclave_
  ...
  result
compiles to
let f x =
  ...
  result
The point is operational: ordinary calls get a fresh allocation-stack region; exclave_ moves result construction to the parent region instead. Despite the name, this is not the function call stack: OxCaml uses a separate allocation stack, and regions describe when parts of that allocation stack can be reclaimed.

How OxCaml manages the allocation stack: tail calls

Tail-call function

let rec loop x =
  ...
  loop next_x
compiles to
let rec loop x =
  start_new_region ();
  ...
  end_current_region ();
  tail call loop next_x

Non-tail call

let f x =
  ...
  g x [@nontail]
compiles to
let f x =
  start_new_region ();
  ...
  let result = g x in
  end_current_region ();
  result

[@nontail] suppresses the tail call, so the region ends only after the call returns.

A tail call is not a normal return of a variable. The current region must be cleared before control transfers to the next call. Explain why OxCaml made this choice: tail-recursive loops should not accumulate allocation-stack space as they go. Use [@nontail] when a local value must stay alive during the call.

How OxCaml manages the allocation stack: mid-function exclave_

Middle exclave_

let f x =
  let n = compute_count x in
  exclave_
  build_result n
compiles to
let f x =
  start_new_region ();
  let n = compute_count x in
  end_current_region ();
  build_result n

If exclave_ is at the beginning, OxCaml starts the region and ends it immediately.

That has the same effect as not starting a region.

The subtle case is not an entirely exclaved function. Work before exclave_ still belongs to the function's own region; the region ends at the exclave_ point.

Local parameters prevent escape

The with_scratch body can use the temporary state during the call, but cannot retain it, and this is forced by the @ local parameter.

Ex03_with_scratch_local_function.ml
type scratch = { mutable total : int } let with_scratch (f : scratch @ local -> 'a) = let s = stack_ { total = 0 } in f s [@nontail] let add_with_scratch x y = with_scratch (fun s -> s.total <- x + y; s.total)

Submoding: use global data locally

escape xs type-checks because xs already has global mode.

sum xs then uses the same value at the more restrictive @ local mode.


@ local data is not always on the allocation stack. Heap data can be used locally too. Stack data cannot be used as global.

Ex03_submoding_global_inner_used_locally.ml
let saved : int list option ref = ref None let escape xs = saved := Some xs let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x :: xs -> x + sum xs let demo () = let xs = [1; 2; 3] in escape xs; sum xs let () = print_endline (string_of_int (demo ()))
Submoding is safe weakening: a global value can be used by an API that only promises local use.

Plain local containers lose the global mode

The inner list starts global: the first escape inner type-checks.

After matching through outer : int list list @ local, the extracted inner is only local.


An ordinary list node does not remember that its element was global. Using the outer list at local mode also uses everything reached through it at local mode.

Ex03_plain_local_outer_list_forgets_global_inner.ml
let saved : int list option ref = ref None let escape xs = saved := Some xs let demo () = let inner = [1; 2; 3] in escape inner; let outer = stack_ [inner] in match outer with | [] -> () | inner :: _ -> escape inner
The point is precision loss through an ordinary constructor field, not that the original heap list became unsafe at runtime.

Modalities preserve the global mode for inner data

The outer list is local, while the inner list is global.

A local list of global lists: the field modality preserves the global mode.

Ex03_global_wrapper_preserves_inner_list_globality.ml
type 'a global = { global : 'a @@ global } let saved : int list option ref = ref None let escape xs = saved := Some xs let demo () = let inner = [1; 2; 3] in escape inner; let outer = stack_ [{ global = inner }] in match outer with | [] -> () | inner :: _ -> escape inner.global
Phrase this as a field-boundary rule, not a cast. The wrapper can only be built from a global value.

Locality: the heap and stack picture with modalities

Make the distinction explicit: runtime heap placement is not the same thing as the current compile-time mode.

Some types do not care about locality: mode crossing

Immediate

let id_local_int (x : int @ local) : int =
  x

No lifetime-sensitive heap block.

Pointer

let id_local_string
  (x : string @ local) : string @ global =
  x

Rejected: the string may point into a local region.

This prepares the representation section: locality depends on whether there may be a pointer whose lifetime matters.

Quiz: requirements or promises?

Argument position

'a @ local -> 'b
'a @ portable -> 'b
'a @ contended -> 'b

Which ones are promises to the caller, and which ones are requirements on the caller?

Result position

'a -> 'b @ local
'a -> 'b @ portable
'a -> 'b @ contended

Which ones are promises to the caller, and which ones are requirements on the caller?

Answer: before the arrow, the caller must be able to provide the argument at that mode. After the arrow, the function promises that the result is available at that mode. For locality, an argument at @ local is an easy requirement that also tells the caller the function will not make the argument escape.

Runtime model

The runtime, GC, and compiler all agree on one value representation. Polymorphic functions are only compiled once.

The uniform model is a strength before it is a cost.

Plain values: immediate word or pointer word

Integer source

let plain_value_integer = 5

Run-time layout

Tuple source

let plain_value_tuple = (1, 2, 3)

Run-time layout

A tuple is still one OCaml value, but that value word points to a heap block.

Boxed numeric values add allocation

Source

let boxed_numeric_values =
  (3.5, 456L)

Run-time layout

The tuple points to separate blocks for the boxed numeric payloads.

This is the concrete cost: extra blocks and pointer hops.

Unboxed types remove specific boxes

Source

let unboxed_numeric_values =
  #(#3.5, #456L)

Run-time layout

The product components are carried directly as raw words.

Contrast this with the previous boxed numeric example.

Unboxed records can inline their fields

Source

type unboxed_point =
  #{ x : float#; y : float# }

type sample =
  { label : string
  ; point : unboxed_point
  ; count : int
  }

let outer_record_with_unboxed_point =
  { label = "p"
  ; point = #{ x = #1.0; y = #2.5 }
  ; count = 7
  }

Run-time layout

Point out the mixed block: scanned value fields first, raw float words after.

or_null uses null or the payload representation

Missing ordinary option

let ordinary_none_int_option = (None : int option)

Present ordinary option

let ordinary_some_int_option = Some 7

Missing or_null

let or_null_null_value = (Null : int or_null)

Present or_null

let or_null_this_int = (This 7 : int or_null)

Each diagram is one root value. Some 7 allocates a wrapper block; This 7 is represented like the integer payload.

Do not go into nested or_null here unless someone asks.

or_null cannot be nested

Null already uses the all-zero word.


If the inner type is string or_null, it already may be null. The outer or_null would need the same null word for a second missing case.


The kind tracks this: or_null needs a non-null value payload, but string or_null has kind value_or_null.

or_null_cannot_be_nested.ml
type nested = string or_null or_null
Explain this as representation ambiguity first, then as the kind distinction value vs value_or_null.

Ordinary polymorphic functions expect values

duplicate is inferred for ordinary one-word values.


An unboxed point has layout float64 & float64, so it is not accepted as that argument.

ordinary_duplicate_rejects_unboxed_point.ml
type point = #{ x : float#; y : float# } let duplicate x = (x, x) let bad = duplicate #{ x = #1.0; y = #2.0 }
The point is the argument kind. Do not frame this as an unboxed return problem.

Kinds say which representation a type parameter accepts

The kind annotation says the argument may have the unboxed point layout.


(The result is still a boxed record in this example.)

kinded_duplicate_accepts_unboxed_point.ml
type point = #{ x : float#; y : float# } type ('a : float64 & float64) duplicated = { first : 'a ; second : 'a } let duplicate_unboxed : ('a : float64 & float64). 'a -> 'a duplicated = fun x -> { first = x; second = x } let ok = duplicate_unboxed #{ x = #1.0; y = #2.0 }
This keeps a boxed result while changing what representation the type parameter can range over.

Templates reduce repetition

Template source

let%template[@kind k = (value, value & value)] id
  : ('a : k). 'a -> 'a =
  fun x -> x

Schematic expansion

let id_value
  : ('a : value). 'a -> 'a =
  fun x -> x

let id_product
  : ('a : value & value). 'a -> 'a =
  fun x -> x

One source pattern can generate multiple checked definitions with different calling conventions.

OxCaml is a work in progress. Future kind-polymorphic definitions are intended to reduce this template pattern.

Keep this as recognition material, not a deep ppx_template lesson. The current library pattern uses templates, but the long-term design direction is more general kind polymorphism.

Representation recap

Ordinary values

One word: immediate data or pointer to a heap block.

Unboxed layouts

Remove selected product or record boxes where the layout is used.

or_null

Like option, but does not allocate.

Keep this as the final mental model before the course-level recap.

OxCaml

Safe high-performance programming.

Parallel work

Use more cores without introducing data races.

Stack allocation

Avoid heap allocation without creating dangling stack pointers.

Unboxed representation

Remove boxes and pointer hops without representation mismatches.
