A small stack allocation example

Stack allocate values with stack_.

OxCaml can often infer stack allocation; stack_ makes it a requirement.

The current allocation region is cleared before the function returns.

Ex01_stack_sum.ml
(* Stack allocation example. *) let rec sum xs = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in (* xs gets deallocated here *) n let () = let n = sum3 1 2 3 in print_endline (string_of_int n)

Stack allocated values cannot escape their region

A callee cannot secretly keep a stack-allocated value after the caller region is gone.

Expected outcome: the call to sum is rejected.

Ex01_stack_sum_escape.ml
(* Stack allocation example. *) let saved = ref [] let rec sum xs = match xs with | [] -> 0 | x::xs' -> saved := xs :: !saved; x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in (* xs gets deallocated here *) n let () = let n = sum3 1 2 3 in print_endline (string_of_int n)

Returning stack allocated values cannot escape their region

The integer result can return, but the stack-allocated list cannot.

Expected outcome: returning xs is rejected.

Ex01_stack_sum_return_escape.ml
(* Stack allocation example. *) let rec sum xs = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in (* xs gets deallocated here *) n, xs let () = let n, _xs = sum3 1 2 3 in print_endline (string_of_int n)

But sometimes we want to return stack allocated values

exclave_ builds the returned value in the caller's region.

Ex01_stack_sum_exclave_return.ml
(* Stack allocation example. *) let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = exclave_ let xs = stack_ [a;b;c] in let n = sum xs in n, xs let () = let n, xs = sum3 1 2 3 in print_endline (string_of_int n); print_endline (string_of_int (sum xs))

How OxCaml manages the allocation stack

Normal functions get their own region.

Normal function

let f x =
  ...
  result
compiles to
let f x =
  let region = start_region () in
  ...
  end_region region;
  result

start_region () returns the current allocation stack pointer.

end_region region resets the allocation stack pointer to that saved pointer.

exclave_ uses the parent region.

exclave_ result

let f x =
  exclave_
  ...
  result
compiles to
let f x =
  ...
  result

How OxCaml manages the allocation stack: tail calls

Region ends before tail calls.

Tail-call function

let rec loop x =
  ...
  loop next_x
compiles to
let rec loop x =
  let region = start_region () in
  ...
  end_region region;
  tail call loop next_x

[@nontail] keeps the region open, so stack values can be passed to the call.

Non-tail call

let f x =
  ...
  g x [@nontail]
compiles to
let f x =
  let region = start_region () in
  ...
  let result = g x in
  end_region region;
  result

How OxCaml manages the allocation stack: mid-function exclave_

Middle exclave_

let f x =
  let xs = compute_list x in
  let n = sum xs in
  exclave_
  build_result n
compiles to
let f x =
  let region = start_region () in
  let xs = compute_list x in
  let n = sum xs in
  end_region region;
  build_result n

If exclave_ is at the beginning, OxCaml starts the region and ends it immediately.

That has the same effect as not starting a region.

Every value

Values have locality, just as they have types. OxCaml tracks the locality of every variable and expression.

Function signatures specify locality.

Locality is deep

Locality rules for stack_ and exclave_

Local parameters prevent escape

Submoding: use global data locally

escape s type-checks because s already has global mode.

length s then uses the same value at the more restrictive @ local mode.


@ local data is not always on the allocation stack. Heap data can be used locally too. Stack data cannot be used as global.

Ex01_submoding_global_string_used_locally.ml
let saved : string list ref = ref [] let escape (s : string @ global) = saved := s :: !saved let length (s : string @ local) = String.length s let global_string @ global = "hello" (* the string is global *) let demo () = escape global_string; (* allowed because global_string is global *) length global_string (* global_string is submoded to local *) let () = print_endline (string_of_int (demo ()))

Problem: plain local containers lose the global mode

The top-level string starts at @ global.

After matching through outer : string list @ local, the extracted inner is only local.


An ordinary list node does not remember that its element was global. Using the outer list at local mode also uses everything reached through it at local mode.

Ex01_plain_local_container_forgets_global_string.ml
let saved : string list ref = ref [] let escape (s : string @ global) = saved := s :: !saved let length (s : string @ local) = String.length s let global_string @ global = "hello" (* the string is global *) let demo () = escape global_string; (* allowed because global_string is global *) let outer = stack_ [global_string] in (* global_string is submoded to local *) match outer with | [] -> () | inner :: _ -> escape inner (* we lost the information that the list elements are @ local *)

Solution: modalities

Default: locality is deep

type 'a box = { field : 'a }

r : 'a box @ global
r.field : 'a @ global

r : 'a box @ local
r.field : 'a @ local

Ordinary field projection uses the locality of the record value.

@@ global field

type 'a box =
  { field : 'a @@ global }

r : 'a box @ global
r.field : 'a @ global

r : 'a box @ local
r.field : 'a @ global

The field stays global even when the record value is local.

Construction

type 'a box =
  { field : 'a @@ global }

let r =
  stack_ { field = inner }

r : 'a box @ local
inner : 'a @ global

Even a local record requires the field value at @ global.

A field modality is an exception to ordinary deep mode propagation.

Modalities preserve the global mode for inner data

The outer list is local, while the inner string is global.

A local list of global strings: the field modality preserves the global mode.

Ex01_global_wrapper_preserves_inner_string_globality.ml
type 'a global = { global : 'a @@ global } let saved : string list ref = ref [] let escape (s : string @ global) = saved := s :: !saved let demo () = let inner @ global = "hello" in escape inner; (* allowed because inner @ global *) let outer = stack_ [{ global = inner }] in (* modality preserves @ global *) match outer with | [] -> () | inner :: _ -> escape inner.global (* allowed because inner.global @ global *)

Two Ways to Run Work in Parallel

fork_join2

  Toy.fork_join2
    (fun () -> left_work ())
    (fun () -> right_work ())
in
combine left right

Children run in parallel; parent resumes after both finish.

spawn

let _ =
  Toy.spawn (fun () -> worker ())
in
parent_side_effect ()

Spawned worker runs in parallel; parent continues immediately.

What is a data race?

danger shape 1: two writes

  (fun _ -> incr r)

danger shape 2: one write and one read

  (fun _ -> incr r)
  (fun _ -> !r)

overlap rule

readsaferace

Two parallel reads are fine. Two racing writes are not allowed. A racing read and write is not allowed either.

Function Boundaries: Shareable

shareable function

A structured fork/join function may still use captures in shared/read-only mode, but not in uncontended/write-capable mode.

Parallelism recap

0. Parallel mutation can race.

1. Simple model: functions passed to parallel work are checked.

  • Fork/join can read but not write captured mutable fields.
  • Spawn can neither read nor write captured mutable fields.

2. Reads and writes are checked using the contention axis.

3. Functions are checked using the portability axis.

What makes OxCaml great

  • Ordinary sequential code does not change.
  • Purely functional code can be parallelized without restrictions.
  • Code that uses mutation internally can still be parallelized.
  • Only code that uses shared mutation is restricted.
