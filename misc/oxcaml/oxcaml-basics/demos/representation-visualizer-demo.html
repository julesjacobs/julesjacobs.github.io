Data Representation And Unboxed Types

A short OxCaml tutorial for reading native OCaml values as bytes, then using that model to understand what unboxed types buy us.

Numeric and pointer words show bytes in the same left-to-right order as the printed raw word, so 0x03020100 appears as 03 02 01 00. String payloads are shown in memory order so the characters read naturally.

1. The Normal OCaml Value Model

Most OCaml values have layout value. At runtime, a value is either an immediate word or a pointer to a heap block. Small integers are immediates: the integer is shifted left and the low bit is set, so 5 appears as raw word 0x...0b.

Heap blocks have a header word followed by payload words. The block frame shows the total size in bytes, including the runtime header word. The decoded header word shows the block tag, the allocated payload size, and how much of that payload the GC may scan.

let small_integer = 5 let tuple_of_three_immediates = (1, 2, 3) let option_values = (None, Some 5)

OxCaml's or_null type is a non-allocating option-like type. Null is the raw machine word zero, while This v is represented the same way as v.

let null_string = (Null : string or_null) let or_null_strings = ( (Null : string or_null) , (This "present" : string or_null) ) let or_null_immediates = ( (Null : int or_null) , (This 42 : int or_null) ) type quote = { symbol : string ; bid : int or_null ; ask : int or_null } let record_with_or_null_fields = { symbol = "OX" ; bid = This 101 ; ask = Null }
The name above the first word labels the binding's value word; it is not a heap block and might live in a register, stack slot, global slot, or other root location. If that value is a heap pointer, it points to a numbered heap block such as @1. Numbered heap blocks start with a decoded runtime header word, followed by payload words. A label like int 5 is an immediate field, null is the raw word zero, and -> @2 is a pointer field.

2. Algebraic Data Types Are Tags Plus Payloads

Algebraic data types use the same value model. A constructor with no payload is an immediate integer. A constructor with payload is a heap block: the header tag identifies the constructor, and the payload words hold that constructor's arguments.

type color = Red | Green | Blue let constant_constructors = (Red, Green, Blue) type shape = | Unit_circle | Point of int * int | Named_point of string * int * int let variant_payloads = ( Unit_circle , Point (3, 4) , Named_point ("origin", 0, 0) )

Inline-record constructors have the same runtime shape as payload constructors. The source gives names to the fields, but the block still stores payload words in order.

type event = | Heartbeat | Quote of { symbol : string; bid : int; ask : int } let inline_record_constructor = Quote { symbol = "OX"; bid = 101; ask = 103 }

Recursive ADTs are heap graphs too. The empty case is an immediate; each non-empty case is a block pointing at its head value and tail value.

type 'a small_list = | Nil | Cons of 'a * 'a small_list let recursive_list_adt = Cons ("a", Cons ("b", Cons ("c", Nil))) type tree = | Leaf of string | Node of tree * tree let leaf = Leaf "shared" let shared_adt_subtree = Node (leaf, leaf)
Runtime tag 0 is shared by tuples, records, and the first payload-carrying constructor of an ADT. Other payload constructors use nonzero tags, so the header word is the place to look when comparing ADT cases.

3. Blocks Form A Graph

The runtime representation is a graph, not a tree. If two fields point to the same heap object, the visualizer gives that object one node id and both fields point to it.

Strings are no-scan blocks: the GC does not treat their payload as pointers. The byte cells show the string contents, the zero byte after the contents, and the final padding-count byte used by this runtime.

let shared = "shared" let same_string_used_twice = (shared, shared) let different_strings = ("left", "right") let long_string_spans_words = "abcdefghijklmnopqrstuvwxyz0123456789" let bytes_payload = Bytes.of_string "mutable bytes span words too"

4. Numeric Widths Show Up In Blocks

Normal ints and chars are immediates. But boxed fixed-width integers such as int32, int64, and nativeint are heap blocks.

let boxed_integer_widths = (42, 'A', 42l, 42L, 42n)

OxCaml also has unboxed numeric types. A value-graph visualizer cannot start from a bare int8# or int64# because those are not ordinary values. Arrays give the first boxed containers where we can inspect their raw storage.

let unboxed_numeric_arrays = ( [| #1s; #2s; #3s; #4s |] , [| #100S; #200S; #300S |] , [| #0x03020100l; #0x07060504l |] , [| #0x0807060504030201L; #0x1817161514131211L |] , [| #1.5s; #2.5s |] )

Unboxed numeric arrays are also not ordinary value arrays. Their runtime tags distinguish specialized raw-storage array representations; those tags are representation tags, not source-level ADT constructor tags.

type smalls = #{ i8 : int8#; i16 : int16#; i32 : int32#; f32 : float32# } type numeric_payload = { name : string ; smalls : smalls ; i64 : int64# ; boxed_i32 : int32 ; boxed_i64 : int64 ; normal_int : int } let unboxed_numeric_fields = { name = "small and large numeric payloads" ; smalls = #{ i8 = #42s; i16 = #32000S; i32 = #0x03020100l; f32 = #1.5s } ; i64 = #0x0807060504030201L ; boxed_i32 = 42l ; boxed_i64 = 42L ; normal_int = 42 }

Records show the same idea inside a mixed block. This record puts several widths in one block. The byte, half-word, word, double-word, native word, single-precision float, and double-precision float fields all live as raw fields next to ordinary value fields.

type width_record = { label : string ; byte : int8# ; half : int16# ; word : int32# ; double_word : int64# ; native_word : nativeint# ; single_float : float32# ; double_float : float# ; ordinary_int : int } let record_of_various_widths = { label = "mixed widths" ; byte = #0x7fs ; half = #0x1234S ; word = #0x03020100l ; double_word = #0x0807060504030201L ; native_word = #0x10203040n ; single_float = #1.5s ; double_float = #2.5 ; ordinary_int = 42 }
The unboxed numeric fields are raw data inside the record's mixed block. The boxed int32 and int64 fields are still pointers to separate heap blocks. In the various-width record, the header's scan 2 w field says that the first two payload words are scannable values; the raw numeric fields come after that.

5. Floats Show Why Representation Matters

A normal float is a value, so a standalone float must be boxed. That box contains the raw IEEE-754 bits. But OCaml has special flat representations for arrays of floats and records made entirely of floats, so those do not need one box per float.

let boxed_float = 3.5 let float_array = [| 1.0; 2.5 |] type point = { x : float; y : float } let all_float_record = { x = 1.0; y = 2.5 }
Floats give the simplest motivation for layouts: two source-level types can both feel like numbers, but need different runtime treatment if one is a normal boxed value and one is raw floating-point bits.

6. OxCaml Makes More Representations Expressible

OxCaml adds layouts for data that is not a normal value. A float# has layout float64; an unboxed product has a product layout such as value & float64. The type system tracks these facts so APIs can say what representation they accept.

value ordinary OCaml values: immediates or pointers to heap blocks
immediate pointer-free values such as int
float64 raw unboxed 64-bit floats, written float#
l1 & l2 an unboxed product layout with one component per layout

A normal value visualizer can only start from values. For non-value layouts, the preprocessor uses the declared layout to render one root component per layout component. Some components are a full machine word, while narrower layouts such as int8# and int16# are shown as narrower byte cells. The source stays focused on the compound value itself, without pretending the unboxed product is a heap block.

let unboxed_pair_of_immediates = #(1, 2) let unboxed_pair_with_string = #(7, "inline root, heap string") let unboxed_pair_with_raw_float = #(7, #3.5) let mixed_unboxed_raw_product = #("raws", #0x03020100l, #0x0807060504030201L, #2.5) let small_and_native_unboxed_words = #(#0x7fs, #0x1234S, #0x10203040n, #1.5s)

7. Boxed Versus Unboxed Fields

Compare these two records. The first stores a normal boxed all-float record behind a pointer. The second stores an unboxed record of float#s inline in the outer heap block.

type boxed_point = { boxed_x : float; boxed_y : float } type sample_boxed = { boxed_label : string ; boxed_point : boxed_point ; boxed_count : int } let outer_record_with_boxed_point = { boxed_label = "p" ; boxed_point = { boxed_x = 1.0; boxed_y = 2.5 } ; boxed_count = 7 } type unboxed_point = #{ unboxed_x : float#; unboxed_y : float# } type sample_unboxed = { unboxed_label : string ; unboxed_point : unboxed_point ; unboxed_count : int } let outer_record_with_unboxed_point = { unboxed_label = "p" ; unboxed_point = #{ unboxed_x = #1.0; unboxed_y = #2.5 } ; unboxed_count = 7 }
In the unboxed version, the header's scan 2 w field says that the first two payload words are scannable by the GC, and the remaining words are raw floating-point bits.

8. Unboxed Products Are Not Just Faster Tuples

Unboxed tuples and unboxed records have their own syntax: #(x, y) and #{ field = value }. They are not ordinary boxed tuples with a different spelling. Their layout can be a product of non-value layouts, so they only fit where the type system knows that such a layout is allowed.

For example, an ordinary list cell expects each element to be a single value word. A product such as #(7, #3.5) has two components with different layouts, so an API must say that it accepts that product layout before such a value can fit there.

type score = #(int * float#) type score_row = { row_name : string ; row_score : score } let record_containing_an_unboxed_tuple = { row_name = "score"; row_score = #(7, #3.5) }

The practical lesson is not "always unbox." The lesson is that layout is part of the contract. Use unboxed types when you want to remove a box, an indirection, or a heap allocation from code where that representation matters.
