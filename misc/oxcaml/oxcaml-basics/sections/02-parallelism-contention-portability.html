Parallelism: contention and portability

In this section you will learn how to use parallelism in OxCaml, and how the OxCaml type checker helps prevent bugs like data races.

By the end of this section, you should be able to:

  • run work with structured fork/join and detached spawn;
  • explain why overlapping reads and writes of shared mutable state can cause data races;
  • use contention modes to predict which direct reads and writes are allowed;
  • read mode requirements at explicit argument positions, including calls such as bump_hits x;
  • understand why function values also need portability requirements, especially when they hide mutable state in a closure environment;
  • read callback types such as ('a @ shared -> 'b) @ shareable positionally;
  • explain that fork_join2 and spawn are ordinary APIs whose types require shareable or portable callbacks;
  • choose whether a parallel API should require a shareable or portable callback.

The parallel APIs we will use

Before we talk about modes, it helps to know the two API shapes that motivate them. OxCaml has structured fork/join APIs for work that must finish before the parent continues, and detached spawn APIs for work that may keep running after the parent returns from the call.

Parallel.fork_join2

Run two pieces of work, wait for both to finish, and return both results.

  • The computation starts inside a scheduler.
  • The scheduler provides a Parallel.t capability.
  • Each function receives a nested Parallel.t.
  • The parent resumes only after the join.

Multicore.spawn

Start detached work and let the parent continue immediately.

  • The spawned work may overlap with later parent-side effects.
  • That makes captured mutable state much more dangerous.
  • The spawned function is therefore checked more strictly.
  • In the browser page, a shim runs the function synchronously; native OxCaml can run it in parallel.

The important operational contract is: fork/join waits before returning; detached spawn may outlive the call.

Browser note: these examples use the real scheduler and spawn API names, but the JavaScript playground runs them sequentially behind the scenes. That lets us type-check and experiment in the browser even though JavaScript is not running native OxCaml domains.

Fork/join: run inside a scheduler; call Parallel.fork_join2 with the provided Parallel.t.

(* Worker code: ordinary code we want to run in parallel. *) let bits_to_string bits = let buf = Buffer.create 0 in List.iter (fun bit -> Buffer.add_char buf (if bit then '1' else '0')) bits; Buffer.contents buf (* Parallel computation: fork two workers and join their results. *) let strings_in_parallel parallel = let #(left, right) = Parallel.fork_join2 parallel (fun _parallel -> bits_to_string [true; false; true; true]) (fun _parallel -> bits_to_string [false; true; false; false]) in left ^ "\n" ^ right (* Scheduler entry point: start the fork/join computation. *) let () = let scheduler = Parallel.Scheduler.Sequential.create () in let s = Parallel.Scheduler.Sequential.parallel scheduler ~f:strings_in_parallel in print_endline "The output is:"; print_endline s

Spawn: pass a unit function to Multicore.spawn. In the browser playground the shim runs it immediately; native OxCaml can run it in parallel.

(* Worker code: ordinary code we want to run in parallel. *) let bits_to_string bits = let buf = Buffer.create 0 in List.iter (fun bit -> Buffer.add_char buf (if bit then '1' else '0')) bits; Buffer.contents buf (* Spawn: start the worker function and let the parent continue. *) let () = print_endline "The output is:"; ignore (Multicore.spawn (fun () -> print_endline (bits_to_string [true; false; true; true])) ()); print_endline (bits_to_string [false; true; false; false])

In both examples, bits_to_string creates its buffer inside the function. Each call gets a fresh buffer, so the compiler infers that this function is safe enough to call in parallel. In the inferred interface, that shows up as @@ portable; we will define that mode precisely below.

Parallelism plus mutation can cause bugs

Parallelism means two pieces of work may make progress at overlapping times. Mutation means the order of steps can affect the result. Together, they make some ordinary-looking refactors unsafe.

The safe version above allocates a fresh buffer on every call. A tempting optimization is to move the buffer outside the function and reuse it. That changes the ownership story: there is no longer one buffer per call, but one buffer shared by every call.

If two calls overlap, they may clear and append to that shared buffer in an interleaved order. That is a data race: the string one call returns may contain pieces of another call's work.

Answer

OxCaml rejects this spawned use of the refactored function. The error says bits_to_string_shared is nonportable: in this context, that means it is not safe to call in parallel.

What counts as a data race?

The bad case is overlapping access to the same mutable state when at least one access writes. Two parallel writes are bad because the final value can depend on which piece of work happens to write last. A read parallel with a write is also bad, because the read may see either the old value or the new value depending on scheduling.

Two parallel reads are fine: neither read changes the state, so their order cannot affect the result. Reads and writes are also fine when the program gives them a defined order, either by ordinary program order or by synchronization. For example, fork_join2 synchronizes after its children finish, so parent code after the fork/join runs after both child computations are done.

Why OxCaml tracks data races in the type system

  • Parallel code often calls existing libraries. The type checker tells you whether those calls are safe in a parallel context.
  • This matters especially for code that was not originally written with parallel callers in mind.
  • Whether a function is safe to call in parallel is recorded in checked module signatures, instead of living in comments you cannot fully trust or being rediscovered every time.
  • The type checker does part of the review for you, so you do not have to manually chase every function body for hidden mutable state.

The rest of this lecture builds the checking model in stages:

  1. Direct reads and writes inside a parallel callback.
  2. Contention modes for captured mutable state.
  3. Mode requirements on explicit function arguments, such as bump_hits x.
  4. Portability requirements on function values, which catch hidden mutable captures.
  5. The API types of fork_join2 and spawn, which impose these requirements without any compiler special case for those function names.

First approximation: parallel callback bodies are checked

When a closure is passed to parallel work, OxCaml checks the closure body under restrictions that prevent data races.

As a first approximation:

  • a fork/join callback may read captured mutable state, but may not write it;
  • a spawned callback may not even read mutable fields, because that read may overlap with a later write in the parent;
  • fresh mutable state created inside the callback is still owned by that callback body.

This approximation is useful, but incomplete. The compiler is not doing a syntactic scan for assignments, and it is not special-casing the names Parallel.fork_join2 or Multicore.spawn. It type-checks ordinary function calls using mode requirements. The next sections make that precise.

Contention modes: mutable access at a use site

OxCaml tracks several mode axes. One of them is the contention axis. Contention controls what kind of access a use site has to the mutable components of a value.

The same source variable can be available at different contention modes in different contexts. In the examples below, x is ordinary mutable state outside the callback. When x is captured by a fork/join or spawned callback, the callback receives weaker access to x.

Contention axis

Contention controls how mutable fields may be used.

x @ uncontended
  • we can read and write x's mutable fields
  • parallel users can access x's immutable fields only
→
x @ shared
  • we can read but not write x's mutable fields
  • parallel users may read x's mutable fields
→
x @ contended
  • we cannot read or write x's mutable fields
  • parallel users may write x's mutable fields

The arrows mean “can be passed to” on the contention axis: if a call site has x @ uncontended, it may pass x to a parameter that only requires x @ shared or x @ contended.

Invariant. For any mutable value x, at any given time OxCaml maintains one of two access patterns:
  • Single writer: one user has write access (x @ uncontended), while any number of parallel users have no access to the mutable parts (x @ contended).
  • Many readers: any number of users have read access (x @ shared).
That rules out parallel writes and write/read races.

Function calls check explicit argument mode requirements

A function call is another operation with mode requirements.

The compiler does not need to inline a helper to know whether the call is allowed. The helper's type records the modes it requires for each explicit argument.

The helper functions below make those argument requirements explicit. Reading the immutable field works with any contention mode, reading the mutable field needs shared or uncontended, and writing the mutable field needs uncontended:

type t = { id : int; mutable hits : int } (* Immutable field reads work even in contended mode. *) let get_id (x @ contended) = x.id (* Mutable field reads need shared or uncontended mode. *) let get_hits (x @ shared) = x.hits (* Mutable field writes need uncontended mode. *) let bump_hits (x @ uncontended) = x.hits <- x.hits + 1

In the inferred interface, focus on the argument modes: t @ contended, t @ shared, and plain t. Plain t means the caller must provide ordinary, uncontended access.

So a call like bump_hits x can fail even when bump_hits itself has no hidden mutable capture. The failure is at the explicit argument position:

available at call site:  x @ shared
required by callee:      x @ uncontended

Buffer operations have argument-mode requirements

Buffer.clear and Buffer.add_char are mutating operations. They require the same kind of access as bump_hits: uncontended access to the buffer.

val clear : Buffer.t @ uncontended -> unit
val add_char : Buffer.t @ uncontended -> char -> unit

This explains the local requirement of the buffer operations: wherever these functions are called, their buffer argument must be available at @ uncontended.

The earlier bits_to_string_shared example has one more layer. The buffer is not passed explicitly to the spawned callback. Instead, the function bits_to_string_shared closes over the shared buffer. That means the spawned callback is not just checking an explicit buffer argument; it is also checking whether the function value bits_to_string_shared is portable enough to call from spawned work. We return to that after introducing portability.

Portability modes: function values and hidden captures

Explicit argument modes explain calls like bump_hits x, where the mutable value is passed directly to the helper.

But a helper can also hide mutable access in its closure environment. In that case, there may be no explicit mutable argument whose contention mode explains the danger. The function value itself must carry a mode requirement.

Closures are values. The portability axis describes whether a value can be used in a parallel context. For closures, this mostly means checking what the closure has captured.

If we define id_x, read_x, and write_x first, then call them later, those helpers still carry their captured x with them:

type t = { id : int; mutable hits : int } let x = { id = 1; hits = 0 } let id_x () = x.id (* a portable function *) let read_x () = x.hits (* a shareable function *) let write_x v = x.hits <- v (* a nonportable function *) let _ = ignore (Multicore.spawn (fun () -> write_x 1) ()); write_x 2

Moving access into helpers does not change the rule

OxCaml still catches the data race hiding behind the helper. The call write_x 1 has no explicit x argument, so the relevant check is on the function value write_x itself. write_x is nonportable because it writes captured mutable state.

Portability controls which parallel contexts a value can be used in. For closure values, this also determines what access the closure may keep to captured state.

Portability axis

Which parallel contexts a value can be used in, and what access closure values keep to captures.

portable
  • can be used in detached parallel work
  • for closures: only immutable-field access to ordinary mutable captures
→
shareable
  • can be used in structured fork/join work
  • for closures: read-only access to mutable fields of captures
→
nonportable
  • not promised safe for parallel use
  • for closures: may keep ordinary read/write access to captured mutable state

The arrows mean “can be passed to” on the portability axis: a value available as portable may be passed to a position that only requires shareable or nonportable.

The helper modes can also be written directly. These three functions close over the same x, but each one keeps a different amount of access to it:

type t = { id : int; mutable hits : int } let x = { id = 1; hits = 0 } let (id_x @ portable) () = x.id let (read_x @ shareable) () = x.hits let (write_x @ nonportable) v = x.hits <- v

For now, focus on the source annotations. id_x is portable because it only uses the immutable field. read_x is shareable because it reads mutable state. write_x is nonportable because it writes mutable state.

Explicit argument vs hidden capture

These two failures look similar but are checked for different reasons.

Explicit argument:

let bump_hits (x @ uncontended) =
  x.hits <- x.hits + 1

fun _parallel -> bump_hits x

The captured value x is passed explicitly. The call is checked against bump_hits's parameter mode. In a fork/join callback, captured x is available only as shared, but bump_hits requires uncontended.

Hidden capture:

let write_x v =
  x.hits <- v

fun _parallel -> write_x 1

Here x is not passed explicitly. The mutable access is hidden in the closure environment of write_x. The call is checked against the portability mode of the function value write_x.

For any call inside parallel work, ask two questions:

  • Are the explicit arguments available at the modes required by the callee?
  • Is the callee value itself available at the portability mode required by this context?

Back to the shared buffer

The shared-buffer example fails because the buffer is hidden in the function value bits_to_string_shared.

let buf = Buffer.create 0

let bits_to_string_shared bits =
  Buffer.clear buf;
  ...

Inside the implementation, Buffer.clear buf and Buffer.add_char buf require buf @ uncontended.

Since buf is captured by bits_to_string_shared, the function value is not portable. A spawned callback may only call portable-enough function values, so this use is rejected:

Multicore.spawn
  (fun () -> bits_to_string_shared bits)
  ()

If the buffer were passed explicitly instead, the failure would be at the buffer argument:

let write_bits (buf @ uncontended) bits =
  Buffer.clear buf;
  ...

fun () -> write_bits buf bits

In that version, the callback has a weakened buf, but write_bits requires an uncontended buffer argument.

Returned function values have modes too

A helper can also receive mutable state explicitly and then return a closure that captures it. That combines both ideas above: the helper call has explicit argument requirements, and the returned function value has its own portability mode.

Returning a function does not bypass the checks. The returned closure still records what it captured and where it may be used.

How captures cross a closure boundary

We have now seen three cases:

  • direct access to a captured value;
  • passing a captured value as an explicit argument;
  • calling a captured function value that hides mutable state.

All three are consequences of the same boundary rule. When a value from the outer scope is used inside a closure with a parallel-safety promise, the value crosses a closure boundary. The closure's required portability mode determines which modes the captured value is available at inside the body.

The diagrams below summarize that boundary behavior. They are not special rules for fork_join2 or spawn; those APIs merely require callback modes that trigger these checks. In the fork/join diagram, assume parallel : Parallel.t @ local is already in scope.

Parallel APIs are ordinary typed APIs

So far we have talked as though the compiler recognizes Parallel.fork_join2 and Multicore.spawn specially. That is only a teaching approximation.

The real rule is that these are ordinary APIs whose types require particular modes on callback arguments.

Schematic fork/join type, omitting details such as once, local, and forkable:

val fork_join2 :
  Parallel.t @ local ->
  (Parallel.t @ local -> 'a) @ shareable ->
  (Parallel.t @ local -> 'b) @ shareable ->
  #('a * 'b)

Schematic spawn type, specialized to the unit-argument shape used in the examples and omitting details such as once, unique, unyielding, and the native result handle:

val spawn :
  (unit -> unit) @ portable ->
  unit -> unit

Calling fork_join2 requires shareable callbacks. That requirement causes captured mutable state inside each callback to be available only with shared/read-only access. Therefore:

  • direct writes to captured mutable state are rejected;
  • calls like bump_hits x are rejected if bump_hits requires x @ uncontended;
  • calls like write_x 1 are rejected if write_x is not shareable.

Calling spawn requires a portable callback. That requirement is stricter. Therefore:

  • direct reads and writes of captured mutable fields are rejected;
  • calls fail if their explicit arguments require stronger modes than the callback has;
  • called function values must themselves be portable enough.

This is the point of the mode system: parallel APIs express their safety requirements in ordinary types, and the compiler checks those requirements compositionally.

Answer

Read the type as a contract for moving work into a fork/join tree.

  • Parallel.t @ local is checked against the implementation of parallel_map. It promises that parallel_map only borrows the scheduler capability while it runs; it will not store it, return it, or let it escape.
  • The outer @ shareable in ('a @ shared -> 'b) @ shareable is a requirement on the explicit callback argument. parallel_map is going to use that callback inside fork/join branches, so the callback value must be available as shareable. This matters most when the callback closes over mutable state, functions, or other portability-sensitive values.
  • The inner 'a @ shared is the mode at which parallel_map will provide each element to the callback. If an element contains mutable state, the callback may read that state but may not mutate it. This is why a callback such as fun x -> bump_hits x fails when bump_hits requires x @ uncontended.
  • The @ shareable on 'a list @ shareable shared is a portability requirement at the input-list position. Pieces of the list flow into the fork/join tree, so the input must be usable in that context. This matters when the element type contains functions or other portability-sensitive values.
  • The @ shared on 'a list @ shareable shared is a contention requirement at the same input-list position. parallel_map only gets read-capable access to the list and to the elements it extracts from it. This matters when elements contain mutable state.
  • Together, @ shareable shared shows that one type position can carry requirements from multiple mode axes.
  • The final @@ portable is a promise checked against the implementation of parallel_map. The function itself does not depend on hidden nonportable state, so it can be used from portable code.

Mode annotation syntax reference

Modes attach to binder and type positions. They are not tied to a simple syntactic category like “data” or “function.”

Examples:

x : t @ shared

The value at this position must be available with shared contention.

f : (unit -> unit) @ portable

The function value at this position must be available with portable portability.

run : ((unit -> unit) @ portable -> unit) @@ portable

The explicit argument to run must be a portable function value, and the value run itself is declared portable at the module boundary.

map : ('a @ shared -> 'b) @ shareable -> 'a list @ shareable shared -> 'b list

The callback value is shareable; the callback receives each element as shared; the input list position carries both portability and contention requirements.

Mode annotation syntax

OxCaml can often infer modes. We write them explicitly when we want to document an API boundary or make an error point closer to the relevant value.

  • On a binder, write the mode after the name: let get_count (x @ shared) = ... or let r @ uncontended = ref 0.
  • On a type annotation, write the mode after the type: let get_count (x : t @ shared) = ....
  • For a function being defined, let (worker @ portable) x = ... puts the mode on the function value worker.
  • For a function value with an explicit type, write the function type in parentheses: let worker : (int -> int) @ portable = ....
  • For a function argument, the same function-value form says what callers must provide: let run (f : (unit -> unit) @ portable) = ....
  • In a module signature, a val item uses @@ for the declared value itself: val f : (int -> int) @@ portable.
  • The same pattern is common for API functions: val run : (unit -> unit) @ portable -> unit @@ portable requires a portable function argument and declares run itself portable.
  • Inside a function type, the source and target can have their own modes: 'a @ uncontended -> 'b @ portable.

Exercise: where does @ portable attach?

The next two blocks differ only by parentheses around the function type. The function body increments a captured reference, so it should fail if worker itself is being checked as portable. Predict which block is accepted.

Answer

The first block is accepted: unit -> unit @ portable parses like unit -> (unit @ portable), so portable is on the result, not on the whole function value worker. The second block fails because (unit -> unit) @ portable does check worker as portable. When the mode belongs to a function value, put that function type in parentheses.

let r = ref 0 let worker : unit -> unit @ portable = fun () -> incr r let r = ref 0 let worker : (unit -> unit) @ portable = fun () -> incr r

Exercise: nested function type precedence

Run the same experiment for a function that returns another function. Does let make : int -> unit -> unit @ portable = ... check the returned function as portable, or do you need int -> (unit -> unit) @ portable?

Answer

The unparenthesized nested form is accepted, but the parenthesized returned-function form fails. So the same rule of thumb applies: if the mode belongs to a function value, put that function type in parentheses.

let r = ref 0 let make : int -> unit -> unit @ portable = fun _ -> fun () -> incr r let r = ref 0 let make : int -> (unit -> unit) @ portable = fun _ -> fun () -> incr r

Worked examples: portability requirements on function values

These examples isolate the closure/function side of the story. The question is what a closure may capture when it promises to be usable from more parallel contexts.

Portable pure functions

On the portability axis, a pure function with no problematic captures is the easy case. The compiler can accept the @ portable annotation because the closure does not depend on thread-local mutable state.

let (factorial @ portable) n = let rec loop acc i = if i <= 1 then acc else loop (acc * i) (i - 1) in loop 1 n

Ordinary closures may capture ordinary refs

Without a portability promise, ordinary OCaml closure behavior is still available. This function captures and mutates a reference. That is fine for an ordinary local closure, but it is exactly the kind of capture we do not want to silently ship to another thread.

let r = ref 0 let ordinary () = r := !r + 1; !r let () = print_endline (string_of_int (ordinary ()))

Portable closures may capture immutable data

Portable closures may still capture immutable data. Capturing factor is safe because the closure does not get a handle to mutable state that can race with another thread.

let factor = 3 let (times_factor @ portable) x = x * factor

Portable closures reject ordinary ref captures

By contrast, capturing an ordinary reference and reading it inside a @ portable closure fails. Inside a portable closure, captured mutable state has a mode too restrictive for ordinary ref access.

Exercise: why does the ref capture fail?

Why is the previous immutable capture accepted while this reference capture is rejected?

Answer

The immutable integer cannot be mutated through the captured value. The reference can be read or written through a mutable cell, so moving the closure into a detached parallel context would need stronger guarantees than an ordinary ref capture provides.

let r = ref 0 let (bad @ portable) () = !r

Portable functions may use fresh local mutation

This brings us back to the opening example. A portable function may allocate fresh mutable state inside each call, use it locally, and return an ordinary result. The closure itself is still portable because that fresh state is not captured from the outside.

let (fresh_ref @ portable) () = let r = ref 0 in r := !r + 1; !r let () = print_endline (string_of_int (fresh_ref ()))

Interface annotations for portable APIs

When these ideas become part of a library boundary, the modes belong in the interface. The implementation can use local mutation internally, but the exposed API should say which values are portable and which operations can be called from portable code.

Here, create promises to produce a portable value, and price promises to work from portable code while only requiring the value in contended mode.

module type Thing = sig type t val create : price:float -> mood:int -> t @ portable @@ portable val price : t @ contended -> float @@ portable end

Reference: portabilizing API signatures

Portabilizing an API means changing its .mli so parallel callers can see the right checked promises. If most values in an interface should be callable from portable code, put @@ portable at the top of the .mli. Inside a module type, write sig @@ portable. Individual declarations can opt out with @@ nonportable.

@@ portable

type t : value mod portable

val create : int -> t
val id : t @ contended -> int
val debug_global_counter : unit -> unit @@ nonportable

The usual goal is to make portable the default for the whole signature, then mark only the exceptional operations as nonportable. That is clearer than adding @@ portable one declaration at a time, because the interface says: this module is ready for checked parallel use except where it explicitly says otherwise.

Do this bottom-up. If B.ml depends on A.mli, then A.mli has to expose portable operations before B.mli can honestly promise that B's operations are portable.

module type Thing = sig @@ portable type t : value mod portable val create : int -> t val id : t @ contended -> int val debug_global_counter : unit -> unit @@ nonportable end module Thing : Thing = struct type t : value mod portable = { id : int; mutable count : int } let create id = { id; count = 0 } let id (x @ contended) = x.id let debug_count = ref 0 let debug_global_counter () = incr debug_count end

Exercise: portabilize a signature

This module has one abstract type, two ordinary read operations, and one operation that touches global mutable state. Rewrite the signature so that portable is the default, only the global operation opts out, and the abstract type says as much as it safely can.

Answer

Put @@ portable on the whole sig, because most of the API should be usable from portable code. Give t the kind value mod portable: the representation has mutable state, so it is not contention-independent, but it does not contain nonportable functions. The immutable field reader can accept t @ contended; the mutable field reader needs t @ shared; the global reset operation must be @@ nonportable.

module Counter : sig @@ portable
  type t : value mod portable

  val create : int -> t
  val id : t @ contended -> int
  val count : t @ shared -> int
  val reset_for_tests : unit -> unit @@ nonportable
end = struct
  type t : value mod portable = { id : int; mutable count : int }

  let create id = { id; count = 0 }
  let id (x @ contended) = x.id
  let count (x @ shared) = x.count

  let all_created = ref []
  let reset_for_tests () = all_created := []
end
module Counter : sig type t val create : int -> t val id : t -> int val count : t -> int val reset_for_tests : unit -> unit end = struct type t = { id : int; mutable count : int } let create id = { id; count = 0 } let id x = x.id let count x = x.count let all_created = ref [] let reset_for_tests () = all_created := [] end

Kinds are the other half of portabilizing signatures. They tell the compiler when values of a type do not need ordinary portability or contention tracking.

  • immutable_data: no function values and no ordinary mutable state, so the type crosses both portability and contention.
  • value mod portable: crosses portability. In basic code, think “ordinary data, possibly mutable, but not containing nonportable functions.”
  • value mod contended: crosses contention. In basic code, think “no ordinary mutable state,” but function values can still appear, so this is not a portability promise.
type immutable_pair : immutable_data = { id : int; name : string } let both (x : immutable_pair @ nonportable uncontended) : immutable_pair @ portable contended = x type mutable_counter : value mod portable = { id : int; mutable count : int } let portable_counter (x : mutable_counter @ nonportable) : mutable_counter @ portable = x type callback_box : value mod contended = { f : int -> int } let contended_callback (x : callback_box @ uncontended) : callback_box @ contended = x
