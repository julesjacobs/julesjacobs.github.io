Value layouts and unboxing

This lecture is about how OCaml values are represented at runtime, why that representation is a good default, and where high-performance code needs more control. We first build the plain OCaml value model, then look at the costs of boxing and indirection, and then introduce the OxCaml features that change the representation.

By the end, students should be able to look at a small value and explain which parts are immediate words, which parts are heap blocks, where pointers and headers appear, and which OxCaml feature would remove a particular box or allocation.

The notes below cover the same ground as the lecture slides, in more depth. The exercises are collected at the end of the page. If you attended the lecture, you can work through the exercises directly; each exercise points back to the section of the notes that explains its concept.

Plain OCaml has a uniform value representation

An OCaml value is one machine word. On a 64-bit runtime, the low bit of that word tells the runtime how to interpret the rest of the word.

The payload words are interpreted according to the block format. Some payload words are themselves OCaml values, so the GC follows them as pointers when needed. Other payload words are raw data, such as float bits or string bytes, so the GC must not treat them as pointers.

The header word tells the runtime how large the block is and how the payload should be scanned. For algebraic data types, the header tag also identifies which constructor with payload a block represents. Constructors with no payload are the simpler case: they are immediate integers, so they do not need a heap block at all.

This uniform model is a strength of OCaml. The GC, polymorphic functions, tuples, records, variants, and many library data structures can all talk about values without knowing the exact source type.

The uniform model has costs

The uniform value model is convenient, but it has costs. Some data cannot fit directly in one immediate word. A standalone float or int64 is boxed: the value word points to a heap block containing the raw bits.

Indirection shows up in nested data

Nested boxed data creates chains of pointers. Here the outer record points to a separate point block. Because the point contains only floats, OCaml uses its specialized all-float-record representation: the point block stores raw float payload words, not pointers to separate boxed float objects.

One representation cannot be optimal for every performance-sensitive path. OxCaml adds ways to express a different representation when cost matters.

OxCaml layouts remove specific boxes

OxCaml layouts remove specific boxes from the uniform value model.

Tuple block

Uniform cost: an ordinary tuple allocates a heap block just to group its fields. Layout version: an unboxed product carries the components directly.

Unlike an ordinary tuple, the unboxed product is not represented by one pointer to a tuple block. Its representation is just its components: here, the immediate integer and the string pointer. Those components can live in separate registers or stack slots.

let unboxed_pair_of_values = #(1, "one")
roots
unboxed_pair_of_values
1int 10
heap
@116 bytes
string, len 3"one"

Numeric boxes

Uniform cost: the boxed numeric example had a tuple block, a boxed float, and a custom block for the int64. Layout version: raw float# and int64# components store the bits directly in the product.

let unboxed_numeric_values = #(#3.5, #456L)
roots
unboxed_numeric_values
float# 3.5int64# 456

Nested record indirection

Uniform cost: the boxed-point example had an outer record pointing to a separate all-float point block. Layout version: the point is an unboxed record, so the outer record stores the two raw float fields inline and removes the separate point block.

That outer record is a mixed block: the runtime records which leading payload words are ordinary values that the GC should scan, and which remaining words are raw numeric data. Mixed-block layout may group the scannable value words before the raw numeric words, so the memory order need not match the source field order exactly.

type unboxed_point = #{ x : float#; y : float# }

type sample =
  { label : string
  ; point : unboxed_point
  ; count : int
  }

let outer_record_with_unboxed_point =
  { label = "p"
  ; point = #{ x = #1.0; y = #2.5 }
  ; count = 7
  }

Option payload allocation

Uniform cost: Some 7 allocates a wrapper block around an immediate integer payload. Layout version: or_null uses Null for the missing case, and This 7 has the same representation as the integer payload itself.

The missing case is represented by the null machine word. Compare this with None above, which is also a single immediate word but uses OCaml's ordinary constructor encoding rather than null.

let or_null_null_value =
  (Null : int or_null)
roots
or_null_null_value

The present case is represented like the payload itself. Here the payload is an immediate integer, so the diagram has no wrapper block around it. Compare this with Some 7 above, where the present case allocates a block.

or_null_this_int

or_null cannot be nested. The null word already means Null, so string or_null or_null would need two meanings for the same representation. The payload type must have room for the null word; it must not already use the null word itself.

This is the first place where we need to name which representations a type may have. The next section calls those representation requirements kinds.

type nested = string or_null or_null

Kinds record which representations are allowed

Once values can have different layouts, APIs need a way to say which layouts they accept. That is what representation kinds are for. Ordinary polymorphism usually assumes value. Unboxed values require signatures that mention layouts such as float64, bits32, bits64, word, or product layouts.

If a compiler error says a type parameter expects value, read that as: this API expects ordinary one-word OCaml values, not arbitrary unboxed layouts.

Here is an example.

type ('a : value) box type bad = float# box

To fix this, we have to specify the kind.

type ('a : float64) box type ok = float# box type ('a : value & float64) pair_box type ok_pair = #(string * float#) pair_box

Abstract types need kinds too

The same issue appears at module boundaries. In a signature, a plain abstract type t defaults to kind value. That is fine for ordinary OCaml values, but it does not match an implementation where t has product layout. The fix is a kind annotation in the signature, such as type t : value & float64, because the layout is part of the calling convention that clients compile against.

Polymorphic code still has a layout

Ordinary polymorphic functions are usually polymorphic over ordinary OCaml values. This version of map says that explicitly: both the input element and the output element have kind value. That matches ordinary lists, whose cons cells store each element as one OCaml value word.

let rec map_value : ('a : value) ('b : value). ('a -> 'b) -> 'a list -> 'b list = fun f xs -> match xs with | [] -> [] | x :: xs -> f x :: map_value f xs let lengths = map_value String.length ["one"; "two"] let () = List.iter (fun length -> print_int length; print_newline ()) lengths

A product layout has a different calling convention. A value of kind value & value, such as #(string * string), is not one value word. It has two value components. Code that stores, passes, or returns such elements must be compiled with that layout in mind.

type ('a : value & value) product_list = | Nil | Cons of 'a * 'a product_list let rec map_product_list : ('a : value & value) ('b : value & value). ('a -> 'b) -> 'a product_list -> 'b product_list = fun f xs -> match xs with | Nil -> Nil | Cons (x, xs) -> Cons (f x, map_product_list f xs) let swapped = map_product_list (fun #(left, right) -> #(right, left)) (Cons (#("left", "right"), Nil)) let rec print_product_list = function | Nil -> () | Cons (#(left, right), xs) -> print_endline (left ^ " " ^ right); print_product_list xs let () = print_product_list swapped

The implementation pattern still looks like ordinary map, but the generated machine code is different. It must know how many registers or stack slots carry an element, which fields the GC should scan, and how to store the result back into the container.

Templates help avoid repeating representation variants

ppx_template reduces layout-specific repetition. When the source pattern is the same but the modes, kinds, or layouts differ, templates generate the needed family of checked variants from one definition.

The ppx syntax looks like this:

let%template[@kind k = (value, value & value)] id : ('a : k). 'a -> 'a = fun x -> x ;; let x = (id [@kind value & value]) #("left", "right");;

The [@kind k = ...] attribute says: generate one copy where k is ordinary value, and another copy where k is the product layout value & value. The source body is the same, but the generated functions can have different calling conventions.

The playground output shows the generated instances. The generated names exist, but callers should not rely on those implementation details. At call sites, code selects the intended instance with a mono-attribute such as (id [@kind value & value]); id [@kind value] is the default instance and can be written simply as id.

For a map-shaped API, the input element layout and output element layout should be separate variables. Base and Core use this pattern for map-like functions: the input can have one kind and the mapped result can have another.

[%%template:
[@@@kind.default ki = (value, value & value)]
[@@@kind.default ko = (value, value & value)]

type ('a : k) vec
[@@kind k = (value, value & value)]

val map
  : ('a : ki) ('b : ko).
    ('a -> 'b)
    -> ('a vec[@kind ki])
    -> ('b vec[@kind ko])]

Syntax expansion templates are temporary. OxCaml is a work in progress, and in the future, proper layout polymorphism will replace templates.

Summary

Plain OCaml uses a uniform value representation: a word that is either an immediate or a pointer to a heap block. OxCaml keeps that model as the default, but lets performance-sensitive code use more precise layouts when a box, pointer indirection, or option allocation is the cost we need to remove.

Kinds record which representations an API accepts. Templates are the current way to repeat one source pattern across several kinds; layout polymorphism is intended to replace that template pattern over time.

Exercise 3: convert hd to or_null

Checks: using Null and This in an API. If stuck: reread Option payload allocation.

Start from the ordinary option-returning hd_option. Write the same API shape with Null and This instead of None and Some.

let hd_option = function | [] -> None | x :: _ -> Some x let hd_or_null xs = failwith "implement this" let value_or default = function | Null -> default | This x -> x let first = value_or "empty" (hd_or_null ["first"; "second"]) let missing = value_or "empty" (hd_or_null [])
Answer key 
let hd_or_null = function
  | [] -> Null
  | x :: _ -> This x

This has the same branch shape as hd_option. The missing case uses the null word, and the present case uses This x, which has the same runtime representation as x instead of allocating a separate Some wrapper.

Exercise 4: fix the product layout

Checks: kind annotations on type parameters. If stuck: reread Kinds record which representations are allowed.

Explain which annotation has to be fixed, then fix it.

type ('a : value) slot = Slot of 'a type bad = #(string * float#) slot
Answer key

The product #(string * float#) has layout value & float64. The annotation on slot should be ('a : value & float64).

type ('a : value & float64) slot = Slot of 'a type ok = #(string * float#) slot

Exercise 5: fix the abstract kind

Checks: kind annotations on abstract types in signatures. If stuck: reread Abstract types need kinds too.

The signature below defaults type t to kind value, which does not match the unboxed implementation. Explain which annotation has to be added to the signature, then fix it.

module type Pair = sig type t val make : string -> float# -> t end module Bad : Pair = struct type t = #(string * float#) let make name score = #(name, score) end
Answer key

Clients still do not know that t is an unboxed product. They do need to know that values of type t use layout value & float64, because that layout is part of the calling convention. The fixed signature says type t : value & float64.

module type Pair = sig type t : value & float64 val make : string -> float# -> t end module Good : Pair = struct type t = #(string * float#) let make name score = #(name, score) end
