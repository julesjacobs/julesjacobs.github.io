Locality and stack allocation

This section is about lifetime. A value has a lifetime: the time when it is valid to use that value.

OxCaml can put short-lived values on the allocation stack instead of the GC heap. That is useful only if the compiler can check that no one uses the value after its region ends.

By the end of this section, you should be able to:

  • explain why stack allocation matters for latency-sensitive code;
  • use stack_ and exclave_ in small examples;
  • explain what the locality axis records;
  • explain why borrowing uses @ local parameters;
  • explain why modes are deep in data structures;
  • use a field modality such as @@ global to keep a global view through a local container.

Why stack allocation matters

OxCaml allocation is cheap, but GC is high latency. Heap allocation creates work for the GC. In low-latency code, that future GC work can be the problem.

Stack allocation is one way to avoid that heap work. The tradeoff is lifetime: a stack-allocated value must not be used after its region ends.

A small stack allocation example

Use stack_ to put new allocations on the allocation stack. In this example, the list xs is used inside sum3. Then sum3 returns only the integer result.

stack_ is shallow. It does not copy values that are already reachable. For example, in stack_ (x, y), the pair can be stack allocated, but x and y keep their existing lifetimes.

let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in (* xs gets deallocated here *) n let () = let n = sum3 1 2 3 in print_endline (string_of_int n)

The important fact is simple: xs is temporary. The allocation stack gets cleared at the end of a function, so xs cannot be used after sum3 returns.

The annotation on sum matters. It says sum may receive a local list, and it will not keep that list.

Stack allocated values cannot escape their region

A stack-allocated value cannot be stored somewhere that may outlive its region. A global reference may outlive the function call, so the code below is rejected.

let saved = ref [] let rec sum xs = match xs with | [] -> 0 | x::xs' -> saved := xs; x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in n let () = let n = sum3 1 2 3 in print_endline (string_of_int n)

The bug would be a dangling pointer: saved would point into a region that has already been cleared.

Returning a stack allocated value is also an escape

Returning the integer n is fine. Returning xs is not fine, because xs points into the current region.

let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = let xs = stack_ [a;b;c] in let n = sum xs in n, xs let () = let n, _xs = sum3 1 2 3 in print_endline (string_of_int n)

Checkpoint: what escapes?

In n, xs, which part is safe to return, and which part is rejected?

Answer

n is safe. It is an integer result. xs is rejected because it points into the current stack region.

Use exclave_ to build a returned local value

Sometimes we do want to return a stack-allocated value. The keyword exclave_ ends the current region and evaluates the following expression in the caller's region.

That means the returned value is not smuggled out of the old region. It is built in the caller's region.

let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x::xs' -> x + sum xs' let sum3 a b c = exclave_ let xs = stack_ [a;b;c] in let n = sum xs in n, xs let () = let n, xs = sum3 1 2 3 in print_endline (string_of_int n); print_endline (string_of_int (sum xs))

How OxCaml manages the allocation stack

The compiler can be explained with two simple operations. A normal function starts a new region. Before the function returns, the current region ends.

Normal function
let f x =
  ...
  result
Region view
let f x =
  start_new_region ();
  ...
  end_current_region ();
  result

An exclave_ result is different. It moves result construction to the parent region.

exclave_ result
let f x =
  exclave_
  ...
  result
Region view
let f x =
  start_new_region ();
  end_current_region ();
  ...
  result

When exclave_ is at the beginning, the function region starts and ends immediately. The result is then built in the caller's region.

Regions end before tail calls

A tail call transfers control to another function instead of returning a value. So the current region ends before the tail call.

Tail call
let rec loop x =
  ...
  loop next_x
Region view
let rec loop x =
  start_new_region ();
  ...
  end_current_region ();
  tail call loop next_x

The attribute [@nontail] suppresses the tail call. Then the region stays alive during the call and ends only after the call returns.

Non-tail call
let f x =
  ...
  g x [@nontail]
Region view
let f x =
  start_new_region ();
  ...
  let result = g x in
  end_current_region ();
  result

exclave_ in the middle of a function

If exclave_ appears after some work, the early work still belongs to the function's region. The region ends at the exclave_ point.

Source
let f x =
  let y = stack_ [1; 2; 3] in
  consume y;
  exclave_
  build_result x
Region view
let f x =
  start_new_region ();
  let y = stack_ [1; 2; 3] in
  consume y;
  end_current_region ();
  build_result x

The result cannot use y, because y was allocated in the region that just ended. The result can use x, because x came from the caller.

If exclave_ is at the beginning, OxCaml starts the region and ends it immediately. The result expression still runs in the caller's region.

The locality axis

The locality axis records how long a value may live. It answers this question: how long does this value live?

Functions and exclave_

After exclave_, values from the old current region are gone. Function arguments can still be used if they came from the caller. Values allocated after exclave_ can also be used.

Source
let f (x : int list @ local) =
let y = stack_ [1; 2; 3] in
ignore (sum y);
exclave_
after exclave_
let z = stack_ [4; 5; 6] in
sum x + sum z
(* not allowed here: sum y *)
Region view
let f x =
start_new_region ();
let y = stack_ [1; 2; 3] in
ignore (sum y);
end_current_region ();
(* y dies here *)
after exclave_
let z = stack_ [4; 5; 6] in
sum x + sum z
(* x came from caller *)
(* z is after exclave_ *)

Checkpoint: which values are alive?

After exclave_, can the function use x, y, and z?

Answer

It can use x because x came from the caller. It cannot use y because y was allocated before exclave_. It can use z because z is allocated after exclave_.

Idiom: borrowing

Borrowing means this: a function may use a temporary value during a call, but it may not retain that value.

The function passed to with_scratch can use the temporary state during the call, but cannot retain it. This is forced by the @ local parameter.

type scratch = { mutable total : int } let with_scratch (f : scratch @ local -> 'a) = let s = stack_ { total = 0 } in f s [@nontail] let add_with_scratch x y = with_scratch (fun s -> s.total <- x + y; s.total)

Exercise: who is restricted?

In scratch @ local -> 'a, is the restriction on callers of with_scratch, or on the function body that receives scratch?

Answer

The restriction is on the body that receives scratch. It may use scratch during the call, but it may not store or return it.

Submoding: use global data locally

A global value can be used through a local view. This is called submoding.

In this example, escape xs stores the list in a global reference. The same list can still be passed to sum, because sum only needs a local view.

let saved : int list option ref = ref None let escape xs = saved := Some xs let rec sum (xs : int list @ local) = match xs with | [] -> 0 | x :: xs -> x + sum xs let demo () = let xs = [1; 2; 3] in escape xs; sum xs let () = print_endline (string_of_int (demo ()))

Plain local containers lose the global view

The inner list starts global. The first escape inner type-checks.

After matching through outer : int list list @ local, the extracted inner is only local.

Reason: modes are deep. A local view of the outer list gives a local view of the elements inside that list.

let saved : int list option ref = ref None let escape xs = saved := Some xs let demo () = let inner = [1; 2; 3] in escape inner; let outer = stack_ [inner] in match outer with | [] -> () | inner :: _ -> escape inner

The original heap list did not become unsafe at runtime. The problem is the view. After going through a local list, the extracted value is viewed as local.

Modalities preserve the global view

A field modality can keep a field stronger than the container around it.

The outer list is local, while the inner list is global. This is a local list of global lists.

type 'a global = { global : 'a @@ global } let saved : int list option ref = ref None let escape xs = saved := Some xs let demo () = let inner = [1; 2; 3] in escape inner; let outer = stack_ [{ global = inner }] in match outer with | [] -> () | inner :: _ -> escape inner.global

This is not a cast. The record can only be built from a value that is actually global. The modality records that promise.

Some values cross locality

Locality matters when there may be a pointer whose lifetime matters. An immediate value such as an int has no heap block, so it can cross from local to global.

let id_local_int (x : int @ local) : int = x

A heap value such as a string does not cross locality by default. If the value is local, returning it as global would let it outlive its region.

let id_local_string (x : string @ local) : string @ global = x

Allocation recap

  • local and global control lifetime and escape.
  • stack_ forces an allocation onto the allocation stack.
  • exclave_ builds a local result in the caller region.
  • @ local parameters express borrowing.
  • @@ global fields preserve the global view through local containers.
