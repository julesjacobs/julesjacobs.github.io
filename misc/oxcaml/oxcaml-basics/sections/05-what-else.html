What Else Is In OxCaml?

The first four lectures cover the core mental model for this course: why OxCaml exists, how modes help with parallelism, how locality controls lifetime and allocation, and how layouts control representation. This final lecture is a map of the surrounding features students should recognize when they see them in real code.

The goal is recognition, not mastery. Students should leave knowing where each feature fits and which earlier idea it extends.

Mode Annotations In APIs

Real signatures can put modes on arguments, return values, function values, fields, includes, and whole signatures. The important question is always the same: which value is being restricted or promised, and who relies on that promise?

Examples to recognize include t @ local, (unit -> unit) @ portable, val f : t @ shared -> int @@ portable, fields such as { callback : (int -> int) @@ portable }, and signature defaults such as sig @@ portable.

Kinds Used With Modes

Some kind annotations are not mainly about unboxed representation. They tell the mode checker facts such as whether a type contains functions or mutable state. That is where signatures such as value mod portable, value mod contended, and immutable_data show up.

These belong in the recognition map because the detailed reasoning has already appeared in the parallelism and locality lectures. Here we only connect the syntax back to the earlier ideas: portability is about parallel-safe use; contention is about mutable-state access; locality is about lifetime.

Templates Avoid Repeating Modal Variants

OxCaml code often needs related definitions across modes, layouts, or kinds. Writing every variant by hand is repetitive, especially for functors and low-level APIs. Template syntax generates those related definitions from one source.

For this course, students only need to recognize that let%template, [@mode], and [@kind] mean that a family of related definitions is being generated.

Specialized Attributes

Some features refine earlier lectures rather than introduce a new topic. Examples include [@zero_alloc strict], [@zero_alloc opt], [@zero_alloc assume], [@@@zero_alloc all], [@local_opt], [@exclave_if_stack], and [@@zero_alloc_if_stack].

The practical rule is to read these as stronger, conditional, or more specialized versions of the allocation and locality contracts from the locality lecture.

Course Boundary

This course should not try to cover every OxCaml feature in detail. The durable outcome is that students can identify which axis a piece of syntax belongs to: parallel safety, lifetime/allocation, representation/layout, or generated variants of those ideas.
