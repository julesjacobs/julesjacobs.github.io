Locality, stack allocation, and zeroalloc

This lecture is about allocation lifetime. OxCaml can put short-lived values on a stack instead of the GC heap, but only when the type checker can prove that no pointer to those values survives after their stack region ends.

By the end of this section, you should be able to:

  • explain why heap allocation matters for latency-sensitive code;
  • describe the basic stack-region model behind local and global;
  • use stack_, local arguments, and local returns in small examples;
  • explain what exclave_ changes about the result's region;
  • understand how stack allocation helps satisfy [@zero_alloc] contracts.

Why heap allocation matters

OCaml allocation is usually cheap. The problem in this section is narrower: some hot paths and low-latency paths should avoid allocating on the GC heap, because heap allocation creates future GC work and can be the point where a GC pause happens.

Start with a harmless-looking helper. Returning Some n is ordinary OCaml style, but it creates an allocated value for the result when the branch is taken.

let maybe_positive n = if n >= 0 then Some n else None let () = match maybe_positive 3 with | None -> print_endline "none" | Some n -> print_endline (string_of_int n)

The point is not that this code is bad. In most code, it is exactly the right style. OxCaml gives us extra tools for the places where allocation behavior is part of the performance contract.

Stack regions

A stack region is a lifetime zone. A value allocated in a region is reclaimed when that region ends, so it must not be used after the region ends. For the first mental model, think of a function body as the region.

The locality mode records this lifetime fact. A local value must not escape the region it belongs to. A global value may escape. Stack-allocated values are local because they would become invalid after the stack region is reclaimed.

At runtime, OxCaml stack allocations are not placed inside ordinary function call frames. They go on a separate allocation stack. The call stack still tracks which functions are active; the allocation stack tracks local blocks and the region marks used to reclaim them.

The sum helper below takes its list @ local, so it may inspect a stack-allocated list but cannot retain it.

Checkpoint: predict whether the list escapes

If a stack-allocated list is built inside a helper and returned as an ordinary result, which region would end too early?

stack_ forces stack allocation

The expression stack_ expr tells the compiler that the immediately following allocation should be placed on the stack. If the value can be used entirely inside the current region, this works as expected.

Here the consumer matters. The list is passed to sum, whose argument is int list @ local. That promise lets callers pass a stack-allocated temporary list. The let total = ... binding also keeps the call to sum out of tail position without using an annotation.

let rec sum_loop acc (xs : int list @ local) = match xs with | [] -> acc | x :: xs -> sum_loop (acc + x) xs let sum (xs : int list @ local) = sum_loop 0 xs let sum_stack_list () = let total = sum (stack_ [1; 2; 3]) in print_endline (string_of_int total) let () = sum_stack_list ()

By contrast, List.length (stack_ [1; 2; 3]) is not the intended example here: the standard List.length interface expects a global list. APIs that consume stack values need local arguments.

stack_ is deliberately strict. If the allocation would have to escape, the compiler rejects the program instead of silently moving that allocation back to the heap.

let bad () = stack_ [1; 2; 3]

The compiler can also infer local values and stack-allocate automatically. The reason to write stack_ is to make the intended allocation placement explicit: if a later refactor would force a heap allocation, you get a compile-time error.

One important detail: stack_ is shallow. In stack_ (x, y), the pair cell is the allocation being forced onto the stack; this does not recursively stack-allocate every value reachable from x and y. A list literal is a compact way to write several nearby cons-cell allocations.

Local arguments let APIs borrow values

A function argument annotated @ local is an API promise made by the callee. It says: this function may be passed a local value, and it will not store, return, or otherwise let that argument escape.

This promise is useful because callers may pass either heap values or stack values. The annotation restricts the function implementation, not the caller.

let inspect (x : int option @ local) = match x with | None -> 0 | Some n -> n let demo () = inspect (stack_ (Some 42)) [@nontail]

Exercise: who is restricted?

In let inspect (x : int option @ local) = ..., is the restriction on callers of inspect, or on the body of inspect?

Answer

The restriction is on the body of inspect. Callers may pass a normal heap option or a stack-allocated option. The callee promises not to let its argument escape.

Callback APIs can lend temporary state

Local arguments are useful even when performance is not the first concern. They let an API lend a temporary value to user code without allowing that user code to retain it.

Here with_scratch creates a temporary mutable record and gives it to a callback. The callback can use the scratch object during the call, but its parameter is local, so it cannot store the scratch object for later.

type scratch = { mutable total : int } let with_scratch (f : scratch @ local -> 'a) = let s = stack_ { total = 0 } in f s [@nontail] let add_with_scratch x y = with_scratch (fun s -> s.total <- x + y; s.total)

If the callback could store s in a global reference, the reference would point at stack storage after with_scratch returns. OxCaml rejects that escape.

type scratch = { mutable total : int } let with_scratch (f : scratch @ local -> 'a) = let s = stack_ { total = 0 } in f s [@nontail] let saved : scratch option ref = ref None let bad () = with_scratch (fun s -> saved := Some s)

Local closures need local callback slots

A closure can also be local. If a closure captures a local stack value, the closure itself must not escape beyond that value's region. Higher-order APIs should mark callback arguments as local when they call the callback immediately and do not store it.

The first version below forces an ordinary, escapable callback type. Passing a closure that captures a stack-allocated counter is rejected.

let bump (r : int ref @ local) = r := !r + 1 let call_now (f : unit -> unit) = f () let bad () = let count = stack_ (ref 0) in call_now (fun () -> bump count)

Now the API says what it actually does: it only borrows the callback. That lets callers pass local closures.

let bump (r : int ref @ local) = r := !r + 1 let call_now (f : (unit -> unit) @ local) = f () let good () = let count = stack_ (ref 0) in call_now (fun () -> bump count); !count

Local returns and exclave_

An ordinary return must be valid after the callee's region has ended. A local return is different: a result type like t @ local says the returned value may be local to the caller's region.

The exclave_ keyword is how we write this. It ends the current region and evaluates the following result-producing expression in the parent region. That is why this helper can return a stack-allocated list as a local result.

let make_stack_list () : _ @ local = exclave_ stack_ [1; 2; 3] let rec sum_loop acc (xs : int list @ local) = match xs with | [] -> acc | x :: xs -> sum_loop (acc + x) xs let sum (xs : int list @ local) = sum_loop 0 xs let use_result () = let total = sum (make_stack_list ()) in print_endline (string_of_int total) let () = use_result ()

Because exclave_ exits the current region, values local to the callee's region cannot be used inside the exclave_. The result has to be built in the parent region, not by smuggling out a value from the region that is ending.

let bad () : _ @ local = let xs = stack_ [1; 2; 3] in exclave_ xs

Locality crosses API boundaries

Locality is not only a local implementation detail. If a helper allocates a temporary value and returns it, the helper's signature must say whether the result is local. Otherwise callers cannot rely on the value living in their region.

This counter module exposes a local-returning constructor. The allocation in make is placed in the caller's region, so the caller can use the counter as a temporary local value.

module Counter = struct type t = int ref let make () : t @ local = exclave_ stack_ (ref 0) let bump (t : t @ local) = t := !t + 1 let get (t : t @ local) = !t end let demo () = let c = Counter.make () in Counter.bump c; Counter.get c [@nontail]

Exercise: choose the boundary

If a module has val make : unit -> t and callers want to use the result as a stack-local temporary, where should the signature change go?

Answer

The constructor should expose a local result, for example val make : unit -> t @ local. Adding local annotations only at the call site cannot move an allocation that already happened inside the callee's region.

Some values cross locality

Locality only matters when there is a lifetime-sensitive heap object involved. An immediate value such as an int has no heap block whose lifetime can become invalid, so it can cross from local to global.

let id_local_int (x : int @ local) : int = x

A heap value such as a string does not cross locality by default. If the value is local, returning it as a global result would allow it to outlive the region it belongs to.

let id_local_string (x : string @ local) : string @ global = x

The later kinds and representation sections explain this more systematically. For now, remember the practical rule: locality tracks whether there may be a pointer whose lifetime matters.

Zeroalloc checks heap allocation

Stack allocation controls where temporary values live. [@zero_alloc] checks a related but distinct contract: this function should not allocate on the GC heap on normal executions.

The annotation is a checker, not an optimization request. If the compiler can prove the contract, the function typechecks.

let[@zero_alloc] add b x y =
  if b then x + y else x

Native zeroalloc check: passes.

A boxed pair is an ordinary heap allocation, so returning a pair from a zeroalloc function fails.

let[@zero_alloc] pair x y =
  (x, y)
Native compiler diagnostic:
Error: allocation of 24 bytes

Local stack allocation is allowed by the zeroalloc checker because it does not allocate on the GC heap and will not trigger a GC.

let[@zero_alloc] local_pair x y : _ @ local =
  exclave_ stack_ (x, y)

Native zeroalloc check: passes.

Zeroalloc across API boundaries

When callers rely on non-allocation, put the contract in the signature. A val[@zero_alloc] declaration does two things: it checks the implementation, and it gives callers a summary they can use without relying on inlining.

module M : sig
  val[@zero_alloc] f : int -> int
end = struct
  let f x = x + 1
end

Native zeroalloc check: passes.

The checker is conservative when it cannot see a callee's allocation behavior. A call through an ordinary function argument may allocate, so this zeroalloc function is rejected.

let[@zero_alloc] apply f x =
  f x
Native compiler diagnostic:
Error: called function may allocate (indirect tailcall)

Exercise: read the zeroalloc failure

In the previous block, is the checker saying that this particular function argument definitely allocates, or that the caller has no checked summary proving it does not allocate?

Answer

It is the second. The checker is conservative around an unknown function value. To make a caller rely on non-allocation, the callee needs a zeroalloc summary in its interface or an explicit checked assumption at the call site.

Additional syntax to recognize later

The basic course path is local, stack_, exclave_, and [@zero_alloc]. Real code also contains stronger or more specialized forms. We should recognize these without making them the main lecture.

  • [@zero_alloc strict]: a stronger zeroalloc contract.
  • [@zero_alloc opt]: a contract checked in optimized/all-check builds.
  • [@zero_alloc assume]: a way to give the checker a trusted summary.
  • [@@@zero_alloc all]: a file-level setting for mostly non-allocating code.
  • [@local_opt]: used in low-level external declarations to support local and global variants.
  • Template helpers such as [@exclave_if_stack] and [@@zero_alloc_if_stack], which we will revisit in the what-else lecture.
