Value layouts and unboxing

This lecture is about how OCaml values are represented at runtime, why that representation is a good default, and where high-performance code needs more control. We first build the plain OCaml value model, then look at the costs of boxing and indirection, and then introduce the OxCaml features that change the representation.

By the end, students should be able to look at a small value and explain which parts are immediate words, which parts are heap blocks, where pointers and headers appear, and which OxCaml feature would remove a particular box or allocation.

For ordinary numeric and pointer words, the byte cells are shown in the same left-to-right order as the printed raw word. For example, a raw word such as 0x03020100 appears as bytes 03 02 01 00. String payloads are the exception: they are shown in memory order so the characters read naturally.

The runtime picture

Start with the one invariant that ordinary OCaml code relies on: an OCaml value is one machine word. On a 64-bit runtime, the low bit of that word tells the runtime how to interpret the rest of the word.

The payload words are interpreted according to the block kind. Some payload words are themselves OCaml values, so the GC follows them as pointers when needed. Other payload words are raw data, such as float bits or string bytes, so the GC must not treat them as pointers.

The header word tells the runtime how large the block is and how the payload should be scanned. For ordinary blocks, the payload is usually either all values or all raw data. For algebraic data types, the header tag also identifies which constructor with payload a block represents. Constructors with no payload are the simpler case: they are immediate integers, so they do not need a heap block at all.

Plain OCaml has a uniform value representation

Most ordinary OCaml expressions produce this same runtime shape: one value word, either immediate data or a pointer to a heap block.

This uniform model is a strength of OCaml. The GC, polymorphic functions, tuples, records, variants, and many library data structures can all talk about values without knowing the exact source type.

let plain_value_integer = 5

A tuple is not stored directly in the root word. The root word points to a heap block. The heap block has a header and then one payload word per tuple field.

let plain_value_tuple = (1, 2, 3)

Records have the same basic shape as tuples: a header followed by payload words. Immutable and mutable fields are both fields in the block; mutability is a property of what the program may do with the field, not a different block shape.

type quote = { symbol : string ; price : int ; mutable size : int } let plain_value_record = { symbol = "OX"; price = 101; size = 7 }

Exercise: identify the value shapes

Before looking at the string and variant visualizations, predict the runtime shape of each source-level construct: a string, an empty-list constructor, and a constructor with payload. Which ones are immediate words, and which ones need a heap block?

Answer

Strings are heap blocks containing raw bytes. The empty-list constructor is an immediate word. A constructor with payload is a heap block; its header tag distinguishes it from the other payload-carrying constructors of the same type.

Variants are also values

Algebraic data types use the same runtime model. A constructor with no payload is an immediate integer. A constructor with payload is a heap block; the header tag tells the runtime which constructor with payload it is.

type color = Red | Green | Blue let constant_constructors = (Red, Green, Blue) type order = | Market | Limit of string * int | Stop of string * int let variant_payloads = ( Market , Limit ("ABC", 100) , Stop ("ABC", 95) )

Recursive data is a graph of these same values. Each constructor with payload allocates a block. Its fields point at other values, which may themselves be immediates or pointers to blocks.

type tree = | Leaf of string | Node of tree * tree let recursive_tree = Node (Leaf "left", Node (Leaf "middle", Leaf "right"))

Heap blocks can be shared

The runtime representation is a graph, not a tree. If two fields point to the same heap object, there is one heap block with two incoming references.

let shared = "shared" let shared_string_tuple = (shared, shared, "other")

The uniform model has costs

The uniform value model is convenient, but it has costs. Some data cannot fit directly in one immediate word. A standalone float or int64 is boxed: the value word points to a heap block containing the raw bits.

let boxed_numeric_values = (3.5, 456L)

Boxing creates heap allocation and pointer indirection. That is often fine. It becomes a problem in code where the cost of many small allocations, cache misses, or GC work matters.

Option values show the same issue. None is an immediate, but Some payload normally allocates a block to hold the payload. These diagrams show the two cases separately, so there is no surrounding tuple block.

let ordinary_none_int_option = (None : int option) let ordinary_some_int_option = Some 7

Indirection shows up in nested data

Nested boxed data creates chains of pointers. Here the outer record points to a separate point block. Because the point contains only floats, OCaml uses its specialized all-float-record representation: the point block stores raw float payload words, not pointers to separate boxed float objects.

type boxed_point = { x : float; y : float } type sample = { label : string ; point : boxed_point ; count : int } let outer_record_with_boxed_point = { label = "p" ; point = { x = 1.0; y = 2.5 } ; count = 7 }

One representation cannot be optimal for every performance-sensitive path. OxCaml adds ways to express a different representation when the programmer knows which cost matters.

OxCaml layouts remove specific boxes

OxCaml layouts remove specific boxes from the uniform value model. They do not make every heap object disappear; they say which parts of a value should stop being ordinary boxed data.

Tuple block

Uniform cost: an ordinary tuple allocates a heap block just to group its fields. Layout version: an unboxed product carries the components directly. The string is still a heap object; the removed box is the tuple block itself.

Unlike an ordinary tuple, the unboxed product is not represented by one pointer to a tuple block. Its representation is just its components: here, the immediate integer and the string pointer. Those components can live in separate registers or stack slots.

let unboxed_pair_of_values = #(1, "one")

Numeric boxes

Uniform cost: the boxed numeric example had a tuple block, a boxed float, and a custom block for the int64. Layout version: raw float# and int64# components store the bits directly in the product.

let unboxed_numeric_values = #(#3.5, #456L)

Nested record indirection

Uniform cost: the boxed-point example had an outer record pointing to a separate all-float point block. Layout version: the point is an unboxed record, so the outer record stores the two raw float fields inline and removes the separate point block.

That outer record is a mixed block: the runtime records which leading payload words are ordinary values that the GC should scan, and which remaining words are raw numeric data. Mixed-block layout may group the scannable value words before the raw numeric words, so the memory order need not match the source field order exactly.

type unboxed_point = #{ x : float#; y : float# } type sample = { label : string ; point : unboxed_point ; count : int } let outer_record_with_unboxed_point = { label = "p" ; point = #{ x = #1.0; y = #2.5 } ; count = 7 }

Exercise: which box disappeared?

Compare the boxed and unboxed versions below. Which heap block disappears in the unboxed version, and which heap objects still remain?

Answer

The outer record still has a heap block, and the string label is still a heap object. The removed block is the separate point block. The two point coordinates become raw fields inside the outer record.

type boxed_point = { x : float; y : float } type boxed_sample = { label : string ; point : boxed_point ; count : int } type unboxed_point = #{ x : float#; y : float# } type unboxed_sample = { label : string ; point : unboxed_point ; count : int }

Option payload allocation

Uniform cost: Some 7 allocates a wrapper block around an immediate integer payload. Layout version: or_null uses Null for the missing case, and This 7 has the same representation as the integer payload itself.

The missing case is represented by the null machine word. Compare this with None above, which is also a single immediate word but uses OCaml's ordinary constructor encoding rather than null.

let or_null_null_value = (Null : int or_null)

The present case is represented like the payload itself. Here the payload is an immediate integer, so the diagram has no wrapper block around it. Compare this with Some 7 above, where the present case allocates a block.

let or_null_this_int = (This 7 : int or_null)

or_null cannot be nested. The null word already means Null, so string or_null or_null would need two meanings for the same representation. The kind system catches this: or_null expects a non-null payload representation, but string or_null is already nullable.

type nested = string or_null or_null

Kinds record which representations are allowed

Once values can have different layouts, APIs need a way to say which layouts they accept. That is what representation kinds are for. Ordinary polymorphism usually assumes value. Unboxed values require signatures that mention layouts such as float64, bits32, bits64, word, or product layouts.

If a compiler error says a type parameter expects value, read that as: this API expects ordinary one-word OCaml values, not arbitrary unboxed layouts.

Exercise: predict the kind bound

The first block says that box only accepts ordinary value-layout types, so float# is rejected. Predict which kind bound is needed, then compare with the fixed block below.

Answer

Use float64 for float#. The fixed block below changes the bound to ('a : float64). For an unboxed pair such as #(string * float#), use the product layout value & float64.

type ('a : value) box type bad = float# box type ('a : float64) box type ok = float# box type ('a : value & float64) pair_box type ok_pair = #(string * float#) pair_box

Exercise: predict the product layout

The first block says that slot only accepts ordinary value-layout types. Predict which product layout accepts an unboxed pair of a string and an unboxed float, then compare with the fixed block below.

Answer

The product #(string * float#) has layout value & float64. The string component is one ordinary value word, and the unboxed float component is one raw float64. The fixed block below uses ('a : value & float64).

type ('a : value) slot = Slot of 'a type bad = #(string * float#) slot type ('a : value & float64) slot = Slot of 'a type ok = #(string * float#) slot

Abstract types need kinds too

The same issue appears at module boundaries. In a signature, a plain abstract type t defaults to kind value. That is fine for ordinary OCaml values, but it does not match an implementation where t has product layout.

Exercise: predict the abstract kind

The implementation below keeps a string and an unboxed float in an unboxed product. Explain why the first signature does not match, then predict the abstract kind used by the fixed signature below.

Answer

Clients still do not know that t is an unboxed product. They do need to know that values of type t use layout value & float64, because that layout is part of the calling convention. The fixed signature says type t : value & float64.

module type Pair = sig type t val make : string -> float# -> t end module Bad : Pair = struct type t = #(string * float#) let make name score = #(name, score) end module type Pair = sig type t : value & float64 val make : string -> float# -> t end module Good : Pair = struct type t = #(string * float#) let make name score = #(name, score) end

Polymorphic code still has a layout

Ordinary polymorphic functions are usually polymorphic over ordinary OCaml values. This version of map says that explicitly: both the input element and the output element have kind value. That matches ordinary lists, whose cons cells store each element as one OCaml value word.

let rec map_value : ('a : value) ('b : value). ('a -> 'b) -> 'a list -> 'b list = fun f xs -> match xs with | [] -> [] | x :: xs -> f x :: map_value f xs let lengths = map_value String.length ["one"; "two"] let () = List.iter (fun length -> print_int length; print_newline ()) lengths

A product layout has a different calling convention. A value of kind value & value, such as #(string * string), is not one value word. It has two value components. Code that stores, passes, or returns such elements must be compiled with that layout in mind.

type ('a : value & value) product_list = | Nil | Cons of 'a * 'a product_list let rec map_product_list : ('a : value & value) ('b : value & value). ('a -> 'b) -> 'a product_list -> 'b product_list = fun f xs -> match xs with | Nil -> Nil | Cons (x, xs) -> Cons (f x, map_product_list f xs) let swapped = map_product_list (fun #(left, right) -> #(right, left)) (Cons (#("left", "right"), Nil)) let rec print_product_list = function | Nil -> () | Cons (#(left, right), xs) -> print_endline (left ^ " " ^ right); print_product_list xs let () = print_product_list swapped

The implementation pattern still looks like ordinary map, but the generated machine code is different. It must know how many registers or stack slots carry an element, which fields the GC should scan, and how to store the result back into the container. That is why real libraries often need separate definitions for different layouts rather than one ordinary polymorphic function.

Templates help avoid repeating representation variants

ppx_template reduces layout-specific repetition. When the source pattern is the same but the modes, kinds, or layouts differ, templates generate the needed family of checked variants from one definition.

The ppx syntax looks like this:

let%template[@kind k = (value, value & value)] id
  : ('a : k). 'a -> 'a
  =
  fun x -> x
;;

The [@kind k = ...] attribute says: generate one copy where k is ordinary value, and another copy where k is the product layout value & value. The source body is the same, but the generated functions can have different calling conventions.

(* Semantic expansion: two checked instances. *)
let id_value
  : ('a : value). 'a -> 'a
  =
  fun x -> x

let id_product
  : ('a : value & value). 'a -> 'a
  =
  fun x -> x

The generated names exist, but callers should not rely on those implementation details. At call sites, code selects the intended instance with a mono-attribute such as id [@kind value & value]; id [@kind value] is the default instance and can be written simply as id.

For a map-shaped API, the input element layout and output element layout should be separate variables. Base and Core use this pattern for map-like functions: the input can have one kind and the mapped result can have another.

[%%template:
[@@@kind.default ki = (value, value & value)]
[@@@kind.default ko = (value, value & value)]

type ('a : k) vec
[@@kind k = (value, value & value)]

val map
  : ('a : ki) ('b : ko).
    ('a -> 'b)
    -> ('a vec[@kind ki])
    -> ('b vec[@kind ko])]

Summary

Plain OCaml gives most data the uniform value representation: a word that is either an immediate or a pointer to a heap block. OxCaml keeps that model as the default, but lets performance-sensitive code use more precise layouts when a box, pointer indirection, or option allocation is the cost we need to remove.
